## 1. 关键架构决策

### 决策 1：全局场景信息条 —— 位置落在页面内容区，不进侧边栏

- 不改动 `components/Sidebar.tsx`。
- 挂载点：`App.tsx` 里 `<div className="flex-1 p-6 overflow-y-auto ...">`（即"Dynamic Content Container"）内部、`{renderContent()}` **之前**，作为该场景"页面内容"的第一部分渲染，随内容区一起滚动，视觉上明确属于"页面里"而不是常驻顶部工具栏。
- 复用 `SciFiCard` 风格做成一条横向信息条，从左到右：场景名称（大字）+ 场景 ID（名称正下方或右侧，小字号次要文字，如 `pm-hydro-11`）Ⅰ 更新时间 Ⅰ 端到端耗时 Ⅰ 场景日志入口。
- **只有"场景日志"允许做成可折叠/展开的目录**（默认收起，点击展开列表）；名称+ID、更新时间、端到端耗时这 3 项必须常显，不做折叠、不需要点击才能看到。

### 决策 1.1（新增，修正）：场景日志的真实含义 —— 是"设备工况日志"，不是"代码修改日志"

- 之前理解有误：场景日志面板里显示的**不是本项目的代码变更记录**（那是 `修改日志.md` 的职责），而是"该场景/设备当前运行工况"的模拟日志，比如巡检记录、参数越限告警、状态切换、维护动作等——即"如果这台设备真的在跑，它会产生什么样的日志"。
- 内容自拟，但要贴近该场景实际工况（比如水轮机场景写振动/温度相关的模拟条目，起重设备场景写吊次/载荷相关的模拟条目），不需要逐场景手写——用一个基于场景元数据（名称/分类/设备关键词）的模板化模拟日志生成器，产出"时间戳 + 级别（信息/告警/故障）+ 内容"的条目列表，量级和语气贴近真实运维日志即可。
- 代码里必须给出清晰的"如何替换成真实日志源"的注释，例如：
  ```ts
  // 2026-07-09 新增：场景工况日志目前为模拟数据（mockScenarioLogGenerator）。
  // 后续接入真实日志源时，把 useScenarioLog() 内部实现换成对真实日志接口/数据库的查询，
  // 返回值需满足 ScenarioLogEntry[]（{ time, level, content }[]）结构，其余展示逻辑无需改动。
  ```
- Phase 4 的 10 个真实后端试点页面，则用真实的数据接收/解析/诊断事件生成日志条目，替代模拟生成器。

### 决策 2：更新时间 & 端到端耗时 —— 语义与 mock/real 切换机制

- **更新时间**：定义为"当前这次进入/渲染该场景，内容渲染完成那一刻的时间戳"，格式化成人类可读的本地时间（如 `2026-07-09 14:32:07`）。每次切换到该场景都会重新计算，不是写死的常量。
- **端到端耗时面板**：两种口径，自动二选一展示：
  - **有真实后端数据的页面**（目前只有 `unit1-predictive`，未来是 Phase 4 的 10 个试点页面）：口径 = "数据传入时间 → 全部前端更新完成时间"（即真实响应耗时，覆盖接口请求/解析/图表刷新等全过程）。
  - **无后端、纯前端展示的页面**（其余全部页面）：口径 = "本次渲染开始 → 渲染完成"，只代表页面渲染耗时。锚点选择"最近一次触发渲染的起点"（即切换到该场景、`activeTabId` 变化的那一刻）而不是用户"打开浏览器整个应用"那一刻——这样每次切换场景都能量出一个有意义的新数值，而不是只有第一次进入才有数据。
- 实现方式：一个共享的场景遥测上下文 `ScenarioTelemetryContext` / `useScenarioTelemetry(scenarioId)`：
  - 默认（无后端页面）：由 `App.tsx` 里挂载信息条的地方统一测量"`activeTabId` 变化 → 新内容首次绘制完成"的耗时和完成时间戳，**不需要逐个修改这 1100+ 个 view 文件**。
  - 试点页面（Phase 4）：页面内部在真实拿到数据、真实完成图表/3D更新后，调用同一个 hook 暴露的 `reportRealTiming(dataInAt, allUpdatesCompleteAt)` 上报真实时间，信息条检测到"本场景有真实上报"就展示真实口径，否则回退到默认自动测量的口径——这就是"两套逻辑随页面接入后端自动切换"的具体做法。

### 决策 3：3D 模型库跳转链接 —— 每页独立占位链接 + 统一可搜索注释标记

- 复用小组件 `ModelLibraryLink`（接收一个 `url` 和展示用的 `label`），贴在每个含 3D 画布页面的 3D 卡片标题栏/角落，不遮挡 3D 视图本体。
- **每个页面的链接必须各自独立、可单独修改**，不用一个全局共享常量。约定统一格式，方便以后一次性批量替换或逐个手改：
  ```ts
  // MODEL_LIB_LINK[<场景id或页面标识>]: 2026-07-09 新增，占位模型库地址；
  // 模型库正式上线后，只需把下面这一行的 url 改成真实地址即可，其余逻辑不用动。
  const modelLibraryUrl = 'https://industrial-intelligent-cockpit.example.com/model-lib/models/<场景id>';
  ```
  （域名沿用项目名 `industrial-intelligent-cockpit` 自拟，仅作占位，不指向真实服务）
- 每次批量接入后，在 `修改日志.md` 对应记录里写明："可通过全局搜索注释关键字 `MODEL_LIB_LINK[<场景id>]` 定位本次新增代码"，方便后续按场景逐个查找、单独替换真实链接。
- 未被 `App.tsx` 引用的目录/文件视为废弃，直接跳过，不做处理（例如已核实的 `views/vibration-monitoring/`、`components/vibration-monitoring/`，无空格版本，实际生效的是带空格的 `views/Vibration monitoring/`）。批量接入每个分类前，先核实该分类下哪些文件真的被路由引用到，只处理有效文件。

### 决策 4：场景导出 —— 四种格式可选 + 总计数/分类计数

- 位置不变：`views/SmartOperationsView.tsx`（工业智能运维全景视图）加一个"导出全部场景"入口，点击后可选择导出格式：**Word / Excel / JSON / Markdown**，四种都要能生成。
- 导出内容：
  - 顶部总计：场景总数、分类总数；
  - 按一级分类分组：每个分类的名称、分类 id、该分类下场景数量；
  - 明细：每个场景的 id、名称、所属分类。
- 技术方案：
  - JSON / Markdown：前端直接拼字符串，浏览器 Blob 下载，无新依赖。
  - Excel：项目已有 `xlsx` 依赖，用它生成 `.xlsx`，无新依赖。
  - **Word：新增 `docx` npm 依赖**，用 `Document`/`Table`/`Packer` 生成规范的 `.docx` 文件；**内容只要标题 + 表格**（总计数/分类计数/场景明细都用表格呈现），不加页眉页脚、落款、公司信息等装饰内容，浏览器端 `Packer.toBlob` 下载。

## 4. 贯穿所有 Step 的约束

1. 每个 step 实施前，先在本文件对应行补充"预期效果"，经你确认后才可修改代码。
2. 新增前端展示一律复用 `SciFiCard` / `SciFiWidgets` 视觉语言（深色底、青色描边、等宽大写标题），不引入新配色体系。
3. 新增内容通过"空白区域插入"或"可折叠面板"方式呈现，不遮挡原有 3D 视图和图表核心可视区；确需调整原布局时，只做等比缩放/挪位，不删除原展示内容（Phase 4 的 10 个"重大修改"页面除外，按用户指示可整体重做）。
4. 不修改现有页面的路由 id、既有接口返回字段结构；新增内容一律新增字段/新增接口，不做破坏性变更（Phase 4 试点页面除外）。
5. **注释规范**：每处新增/改动代码块顶部加一行简短注释，格式参考项目已有风格（如 `constants.tsx` 里的 `//2026.01.19, update`），写清"改了什么、日期"，例如：
   ```ts
   // 2026-07-09 新增：场景信息条挂载点，展示场景ID/更新时间/耗时面板/日志
   ```
   Phase 2 的模型库链接额外要求用 `MODEL_LIB_LINK[<场景id>]` 这个可搜索标记（见决策 3）。
6. 每个 step 完成后，在 [`修改日志.md`](./修改日志.md) 记录：时间、涉及文件、修改内容、影响面、验证方式；Phase 2 额外记录"可搜索定位关键字"；Phase 4 额外记录"重大修改"标记和原页面功能取舍说明。
