# 多页面无响应根因与稳定性修复

## 1. 云端证据

修复前场景库云端状态：

```text
scene-library.service=active/enabled
Release=20260828-145036
NRestarts=0
MemoryCurrent=469,688,320 bytes
MemoryPeak=474,189,824 bytes
主机内存=1.6 GiB
Swap=0
监听=127.0.0.1:3102
3103=空闲
磁盘使用率=50%
```

服务没有崩溃、数据库没有异常重启、磁盘和 inode 也未耗尽。问题是同一台小内存主机上的 Node 模型 Buffer、浏览器 ArrayBuffer、Three.js 解析对象和 WebGL 资源叠加，最终表现为页面或浏览器无响应。

## 2. 问题链

服务端旧逻辑每 30 分钟扫描全部模型展示场景，并调用持久缓存恢复函数。用户访问页面越多，磁盘 manifest 越多，定时器就会把越多历史模型重新读入无上限的 `modelBinaryCache`，即使页面早已关闭也不会释放。

浏览器侧还存在两项放大因素：

- 已完成下载的 ArrayBuffer 最多保留 3 个；
- React 页面卸载只调用 `renderer.dispose()`，没有主动释放 WebGL context；
- 无效上游资源每 30 秒无限自动重试，长期制造 502、下载任务和日志。

因此它不是单一“数据库崩溃”，也不能靠清浏览器缓存作为根治方案。

## 3. 修复内容

服务端：

- 模型内存缓存同时受条目数和字节数限制，默认 8 项/128 MiB；
- 使用最近访问时间做 LRU 淘汰；
- 高并发下载结束后再次收敛预算，避免所有在途项受保护时留下超限缓存；
- 定时刷新只扫描当前驻留模型，不再把所有历史持久模型读入内存；
- `/api/health` 返回 `modelMemoryCache.entries/bytes/maxEntries/maxBytes`，便于监控；
- 磁盘持久缓存保留，淘汰内存不会导致每次都从主项目重新下载。

浏览器：

- 已完成 ArrayBuffer 缓存从 3 个减到 1 个；
- 卸载时释放 render list、renderer 和 WebGL context；
- 无模型可用时最多自动重试 2 次，之后等待人工重试；
- 成功加载或模型版本变化时重置重试计数。

可通过环境变量调节服务端预算：

```text
MODEL_MEMORY_CACHE_MAX_MB=128
MODEL_MEMORY_CACHE_MAX_ENTRIES=8
```

## 4. 实测结果

本地生产模式使用更严格的 3 项/64 MiB 预算，连续加载 10 个不同模型，全部返回 200；缓存始终不超过 3 项，最高约 57.53 MiB。随后同时请求 6 个模型，全部返回 200，完成后缓存回落到 2 项、52,131,756 字节。

专项结果：

```text
MODEL_LOADING_OPTIMIZATION_VERIFY_OK ... browserBuffers=1 serverLru=bounded autoRetry=2
MODEL_VIEWER_STABILITY_VERIFY_OK centerDrift<1e-6 rotation30=0.360000 rotation120=0.360000
```

上线后应同时观察 `systemctl show scene-library -p MemoryCurrent -p MemoryPeak -p NRestarts` 和公开健康接口。若浏览器仍卡顿，先关闭旧 iframe/标签页并强制刷新，使旧 bundle 和旧 WebGL context 退出；这只用于清除旧运行实例，不替代本轮代码修复。
