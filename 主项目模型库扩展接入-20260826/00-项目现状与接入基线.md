### 1.1 外部模型仿真展示方案

该目录记录了最早落地的主项目模型接入能力：

- 接入模型 ID `2326`、`2328`、`2316`、`2310`；
- 业务数据只访问主项目 `three-model-api`，不抓取模型详情页 HTML；
- 场景库后端按白名单读取元数据、选择三维文件、代理下载并校验；
- 前端支持 FBX、GLB、GLTF，使用 Three.js 页面内渲染；
- Dashboard 默认 5 秒轮询，保留 60 个运行期快照；
- 正常、高负荷、故障三种工况走上游 API；
- 健康度、故障预测和报告由场景库本地诊断服务生成，当前属于仿真演示，不是真实机器学习模型；
- 模型默认 36 小时检查更新，最后成功二进制持久化，候选版本成功解析后才无损替换当前模型；
- 上游失败时保留最后成功模型和遥测快照，并提供手动更新、失败提示和连接状态。

该目录中的早期故障结论已被后续部署记录补充：2026-08-20 的四页初始化故障由云端环境仍使用 HTTP 上游地址导致，后续改为 HTTPS 并发布修复版本。历史错误报告仍有排障价值，但不能代表当前必然故障。

与原始 API 文档相比，项目内实施版省略了独立的 `/api/v1/three-model/models/info` AI 元数据接口以及 `model_category=39` 的列表发现能力。当前页面通过 Dashboard 间接消费 AI 元数据，因此四页不受影响；批量扩展模型时则应恢复这两项能力的调查价值。

### 1.2 跨项目门户集成方案

该目录经历了 iframe、qiankun 和再次回到 iframe 的方案演进。当前有效事实是：

- 主平台通过 iframe 加载场景库独立版；
- 场景库 URL 契约为 `/cockpit/?embedded=1&viewId=<页面ID>`；
- `embedded=1` 隐藏场景库自身导航和顶部外壳，`viewId` 定位具体业务页；
- 模型详情跳转由 `scene-library:navigate` / `scene-library:navigate-result` 消息协议完成；
- 场景库只发送固定 `/three-model/detail` 路径和白名单模型 ID，主平台执行自身 `router.push`；
- 主平台内标签开关打开或关闭时，场景库无需两套逻辑；最终呈现由主平台现有标签系统决定；
- 2026-08-17 的 qiankun 微前端说明属于历史方案。仓库仍生成 `dist-microapp`，但不能据此宣称线上当前使用 qiankun；
- 最后已知的联合待办包括主平台分类“首页”叶子转换和 iframe 消息 Origin 白名单热修，是否已经由主平台团队完成，本轮未做现场验证。

## 3. 两类“模型库”能力必须区分

### 3.1 普通场景页模型库链接

`src/scenarioLib/ModelLibraryLink.tsx` 是普通 `<a target="_blank">` 链接组件。当前在 `views/` 下检出 831 个引用文件，绝大多数仍传入逐页占位 URL。

这条链路只负责“跳到模型库”，不会把模型下载到场景库页面中，也不具备 BFF、安全代理、缓存、遥测或诊断能力。

### 3.2 外部模型页面内展示

仿真分析前四页使用完整接入链路：

```text
主项目 three-model-api
  ├─ 模型元数据 / 文件列表 / 模型二进制
  ├─ Dashboard / 工况 / 数据一致性
  ↓
场景库 Express BFF（白名单、超时、格式、50 MB、缓存与持久化）
  ↓
场景库 React 共用页面
  ├─ Three.js 模型视窗
  ├─ 参数卡与趋势图
  ├─ 工况切换与一致性校验
  ├─ 本地健康评估/故障预测
  └─ 资源协同状态与模型详情导航
```

用户提出的“将更多主项目模型接入场景库来显示”与第二类能力一致，应以第二类链路为基线。

## 6. 可直接复用与需要改造的部分

### 6.1 可直接复用

- 同源 BFF 和固定模型白名单；
- GLB → GLTF → FBX 文件选择及前后端双重格式校验；
- 模型内存缓存、磁盘持久化、定时检查、手动刷新和失败保留；
- 配置驱动的指标卡、趋势图、工况切换和评估报告；
- 三节点资源协同展示与通道状态；
- standalone/embedded 页面定位；
- iframe 宿主导航消息协议；
- 双构建、Release 安装、3103 预检、原子切换和回滚流程。

### 6.2 扩展前建议处理

1. 将场景 ID 从手写联合类型改为由模型目录推导，减少每次新增模型的重复修改。
2. 将宿主导航允许模型集合从 `modelCatalog` 派生，消除第二份模型 ID/名称白名单。
3. 将四个轻量包装组件和 `App.tsx` 四条显式路由改为可控的目录驱动渲染，同时保留未知 ID 安全回退。
4. 将 HTTPS 专项验证从固定四模型改为遍历目录，并校验模型 ID 唯一、场景 ID 唯一、名称与详情 URL 一致。
5. 为不同设备补充可配置的视窗方向、缩放、相机和节点联动；当前目录中的 `viewer.rotation/offset` 尚未完整用于 `RemoteModelViewer`。
6. 明确模型大于 50 MB、包含外部贴图的 GLTF、无网格文件、坐标轴异常和多动画模型的处理策略。
7. 将“有完整 Dashboard 的模型”和“只有三维资源的模型”分型。当前 `bootstrap` 同时依赖模型信息和 Dashboard，后者缺失会导致整页初始化失败。

这些是后续实施建议，本轮尚未修改代码。

## 7. 新模型的最低接入条件

完整复用既有展示页时，每个模型至少需要：

- 唯一的主项目模型 ID；
- 与 ID 对应的真实模型名称；
- 固定 HTTPS 详情地址 `/three-model/detail?id=<ID>`；
- 元数据接口可返回模型及文件信息；
- 至少一个可下载且不超过当前上限的 FBX、GLB 或 GLTF 文件；
- Dashboard 返回 `twin_status`、`equipment` 和非空 `bindable_fields`；
- 若需要工况切换，三个 scenario 接口可用；
- 若需要一致性校验，data-sync 接口可用；
- 每个指标的业务中文名、风险方向和权重；
- 页面标题、描述、所属行业/领域、图表分组和故障知识。

若新模型只有三维文件，没有 Dashboard，不能直接宣称已完整接入现有数字孪生模板，需要先确认采用：

- 仅模型与资源信息展示；或
- 场景库本地演示数据；或
- 主项目补齐运行数据 API。

三种方式的数据真实性和页面功能不同，必须在实施前明确标注。

原始接口文档声明：对于工业可视化模型，即使没有 `ai_metadata` 或部分字段缺失，主项目后端也会用 `DEFAULT_METADATA` 返回完整 Dashboard。该声明有利于批量接入，但仍需针对用户清单中的每个实际 ID 做只读调用验证，不能用文档承诺替代现场证据。

## 8. 当前风险与边界

- 最新云端版本只来自 2026-08-21 文档，本轮未登录服务器核对；
- 主平台模型清单及各新模型 API 本轮尚未取得，不能推断所有模型都有 Dashboard；
- 原始 API 支持通过 `model_category=39` 的列表模式发现候选模型，但本轮尚未调用线上列表接口；用户提供清单后应核对清单与接口返回，而不是擅自扩大接入范围；
- 原始 data-sync 响应明细字段为 `fields_comparison`，当前 `ConsistencyResult` 类型却声明为 `fields`；现有 UI 只读汇总值和 summary，因此当前不受影响，若新增逐字段一致性表必须先统一契约；
- 主平台 Origin 热修和分类首页改造的最后状态未知，不应把场景库发布等同于双平台联合完成；
- 当前专项脚本会拒绝超过四个详情 URL，新增模型时必须同步改测试；
- 当前 50 MB 限制可能排除部分复杂模型；提高限制会影响带宽、内存、超时和 Nginx 配置，不能仅改一个常量；
- GLTF 若引用外部 `.bin` 或纹理，当前单文件下载与空基路径解析不一定完整支持，优先要求自包含 GLB；
- 当前前端动画只对 `rpm`、`vibration` 和任意 `abnormal` 状态做通用联动，新设备的部件级动画需要额外配置或实现；
- 全量 TypeScript 检查在历史记录中长期受 7 个既有非法字符文件阻断，新增功能仍需定向检查、专项检查、双构建并如实记录全量结果。
