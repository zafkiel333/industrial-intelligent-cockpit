# 模型加载长时间停留 0% 诊断

> 诊断日期：2026-08-27（Asia/Shanghai）
> 现场样例：`cp-ocean-fleet` / 模型 `5571` / 重型运输船
> 诊断范围：先完成只读诊断与端到端计时；2026-08-27 已按诊断结论完成本地优化，云端发布状态见第 7 节

## 1. 结论

截图模型不是无效文件，场景库服务和 Nginx 也没有卡死。加载长时间停留 0% 是多个因素叠加：

1. 新增模型采用首次访问时按需获取，发布时只验证了 Bootstrap，并未预热 99 个模型二进制；诊断开始时持久缓存只有 5 个模型，`cp-ocean-fleet` 明确为 `modelCache=empty`。
2. 场景库 BFF 使用 `await response.arrayBuffer()` 先把主项目模型完整下载到内存并校验，完成前不会把模型响应交给浏览器；这段时间前端只能显示 0%。
3. 外部客户端到场景库的实际传输速度较低。模型 `5571` 实际为 26,419,436 字节，端到端下载耗时 82.372 秒，平均约 320,732 B/s；同一文件在服务器本机通过 3102 只需 0.011 秒，通过本机 Nginx 只需 0.021 秒，说明瓶颈不在 Node 或 Nginx 的本机吞吐。
4. 前端没有为模型请求绑定 `AbortController`。用户切换页面后，旧页面的模型下载仍在后台继续，占用连接和带宽；连续查看多个模型时，新请求可能在浏览器连接队列中等待，界面继续显示 0%。
5. 首次模型下载完成后，后端活动版本会从元数据指纹切到内容哈希；10 秒连接轮询会改变 `asset.version`，前端可能在第一次浏览器下载尚未结束时启动第二个同文件请求，而旧请求不会被取消。
6. `modelBufferCache` 缓存的是 Promise。第二个页面实例若复用尚未完成的 Promise，只在 Promise 完成后收到 100%，期间收不到原请求的流式进度，因此可见进度会一直停在 0%。

其中 1～3 是截图页面已经取得现场证据的直接原因；4～6 是代码中确定存在、会在切页和慢速网络下放大问题的加载控制缺陷。

## 3. 代码定位

- `server.ts / fetchRemoteModelBinary`：先执行 `Buffer.from(await response.arrayBuffer())`，属于完整缓冲后返回；
- `server.ts / getServableModel`：没有缓存时同步等待首次下载；
- `RemoteModelViewer.tsx / fetchModelBuffer`：浏览器请求没有取消信号；
- `RemoteModelViewer.tsx / modelBufferCache`：复用未完成 Promise 时只在结束后报告 100%；
- `RemoteModelSimulationView.tsx / displayedModel`：连接快照的 `activeVersion` 优先于 Bootstrap 版本；
- `useModelShowcaseConnection.ts`：每 10 秒轮询一次，首次下载期间可能触发版本键变化和第二次获取。

## 4. 建议修复顺序

1. 为每次模型加载建立 `AbortController`，页面卸载、切换模型或版本变化时取消旧请求；
2. 将同一模型的 Promise 缓存改为共享下载任务，并向所有订阅实例广播已下载字节，不能只在结束后回报 100%；
3. 首次加载期间锁定版本键，服务端返回真实 `X-Model-Version` 后只更新版本状态，不重复下载相同内容；
4. 页面分别显示“等待服务端准备模型”“下载模型 xx/xx MB”“解析模型”三个阶段，并增加停滞时间提示；
5. 服务端改为磁盘缓存优先和流式响应，避免每个访问模型都长期常驻 Node Buffer；
6. 发布后按文件大小和访问优先级低并发预热，而不是一次性把 576.81 MiB 全部装入 1.6 GiB 内存；
7. 对 20 MiB 以上模型考虑离线转为经过压缩的 GLB/Draco/KTX2，FBX 保留为源资源。

## 5. 验收建议

- 快速连续切换 10 个模型页面，离开页面后旧模型请求应立即取消；
- 同一模型首次加载只能出现一次有效二进制下载；
- 25 MiB 模型在低速网络下必须持续显示已下载 MB 和速度，不能长时间停留 0%；
- 下载结束后进入“解析中”，避免把主线程解析时间误认为网络停滞；
- 缓存命中后刷新页面不应重新向主项目下载模型；
- 长时间浏览后检查浏览器内存、服务内存、3102 健康状态和持久缓存完整性。

## 6. 验收边界

当前没有可连接的交互式浏览器实例，无法读取用户浏览器的 Network 队列和控制台，因此“具体某次截图是否已经触发重复 GET”尚不能直接取证。服务端状态、模型文件、缓存、端到端测速和代码加载路径均已核对；上述直接原因与代码放大因素已分别标注。

## 7. 已实施优化（2026-08-27）

本次没有采用“把 99 个模型全部预热到进程内存”的高风险方案，而是针对浏览器加载生命周期和版本缓存进行优化：

1. 模型请求绑定 `AbortController`。页面切换、组件卸载且没有其他订阅者时，在下一任务取消旧下载，避免切页后持续占用客户端连接和带宽。
2. Promise 缓存升级为共享模型任务。所有复用同一任务的页面实例会立即收到当前字节数和后续进度，不再在复用期间长期显示 0%。
3. 同一路由的未完成任务在元数据指纹切换为内容哈希时注册版本别名，继续复用原请求；服务端返回的 `X-Model-Version` 也会登记为别名，避免轮询触发同文件第二次下载。
4. 加载界面拆分为“正在准备模型资源”“正在下载三维模型”“模型已下载，正在解析三维结构”三个阶段；下载阶段显示百分比和已下载/总 MiB，解析前先让浏览器绘制阶段提示。
5. 增加两个明确的失败边界：等待响应头超过 75 秒自动终止；下载流连续 30 秒没有收到数据自动终止，并给出可识别错误信息。
6. 模型 URL 已携带内容版本，浏览器请求改用默认 HTTP 缓存；服务端模型响应改为 `private, max-age=31536000, immutable`。同一内容版本刷新或再次访问时可复用已验证响应，内容变化则使用新版本 URL。
7. 浏览器只保留最多 3 个无人使用且已完成的 ArrayBuffer；正在显示或正在下载的任务不被误清理，防止长期浏览后无上限占用内存。
