# 模型清单采集与实施准备

> 状态：等待用户提供具体要求和模型清单  
> 用途：收到清单后逐项填写，作为开发计划、测试矩阵和验收记录的共同输入

## 1. 建议提供的清单字段

| 字段 | 是否必需 | 示例/说明 |
|---|---|---|
| 主项目模型 ID | 必需 | `2326`，必须唯一 |
| 主项目真实模型名称 | 必需 | 以元数据接口实际返回为准 |
| 场景库页面名称 | 必需 | 菜单和页面标题使用的业务名称 |
| 期望场景 ID | 可协商 | 建议 `sim-visual-<英文短名>`，只能含字母、数字、下划线、连字符 |
| 所属栏目与排序 | 必需 | 例如“仿真分析，第 5 位” |
| 页面描述 | 必需 | 一至两句说明展示目标 |
| 领域 | 必需 | 水电、矿山、港航、船舶、通用工业等 |
| 详情页地址 | 可推导但需核验 | 固定 HTTPS `/three-model/detail?id=<ID>` |
| 三维文件格式与大小 | 必需核验 | 优先自包含 GLB，其次 GLTF/FBX；当前上限 50 MB |
| 模型分类 | 必需核验 | 原始文档覆盖 `model_category=39` 工业可视化模型 |
| AI 元数据 | 建议核验 | `/models/info` 返回 `ai_metadata`；缺失时原文声明由 `DEFAULT_METADATA` 兜底 |
| Dashboard 是否可用 | 必需核验 | 原始契约承诺兜底，仍需对每个实际模型 ID 调用验证 |
| 工况接口是否存在 | 必需核验 | normal / high_load / fault |
| 指标字段 | 必需 | field、中文名、单位、正常范围、风险方向 |
| 图表分组 | 必需 | 每组包含哪些 field |
| 故障模式与建议 | 必需 | 故障名称、证据字段、处置建议 |
| 视窗要求 | 可选 | 初始角度、缩放、相机、背景、是否自动旋转 |
| 动画联动 | 可选 | 字段与模型节点/部件的对应关系 |
| 是否需要报告下载 | 可选 | 默认可复用现有 Markdown 报告 |
| 是否需要模型详情跳转 | 必需确认 | 默认纳入宿主白名单并沿用内标签协议 |
| 数据性质说明 | 必需 | 真实、上游模拟、场景库本地演示或混合 |

## 3. 接入分型

### A. 完整数字孪生页面

适用条件：模型元数据、三维文件、Dashboard、工况和字段结构完整。复用当前四页的全部模型、参数、趋势、诊断、工况、连接关系和报告功能。

### B. 模型与资源状态页面

适用条件：模型元数据和三维文件存在，但 Dashboard 或工况接口不存在。只展示模型、元数据、版本、缓存、连接状态和详情入口，不伪造实时数据或健康诊断。

### C. 明确标注的演示仿真页面

适用条件：业务确实需要趋势和诊断演示，但主项目暂未提供运行接口。可使用场景库配置数据，但页面和报告必须明确标注“演示/模拟”，不得显示为上游实时数据。

## 4. 清单收到后的执行顺序

1. 先用 `model_category=39` 列表模式核对用户清单，再对每个 ID 只读核验基本信息、AI 元数据、文件列表、Dashboard、工况、一致性和文件下载；
2. 形成“可完整接入 / 需降级 / 暂不可接入”矩阵；
3. 与用户确认页面名称、排序、数据性质和降级方式；
4. 编写正式开发计划与影响文件清单；
5. 先重构四模型硬编码，再批量增加目录配置；
6. 完成定向类型检查、目录一致性检查、模型专项检查和双构建；
7. 本地或独立端口逐模型验证 bootstrap、model、dashboard、diagnosis、connection；
8. 验证 standalone 与 `embedded=1&viewId=...`；
9. 重新生成正式菜单 manifest，记录节点数和哈希并交付主平台；
10. 若获部署要求，再按独立 Release、哈希、3103 预检、切换、回滚和公网验收流程执行。
