## 1. 执行摘要

四个仿真页面均能通过 API 正常取得：

- 模型基本信息；
- 模型文件列表；
- 文件名、文件 ID、对象存储 key 和预期文件大小；
- Dashboard 实时运行数据；
- 3D 相机、背景色和自动旋转等渲染配置；
- 设备分析和故障预测所需的遥测字段。

但是，当本项目或独立测试程序使用文档规定的模型下载 API 请求实际 FBX 文件时，上游接口没有返回模型二进制，而是返回以下 JSON：

```json
{
  "code": -1,
  "data": {},
  "message": "下载错误，请联系运维人员处理"
}
```

该响应具有以下特征：

- HTTP 状态为 `200`；
- `Content-Type` 为 `application/json`；
- `Content-Length` 为 `95`；
- 没有模型下载应有的 `Content-Disposition`；
- 四个模型均返回完全相同的业务错误；
- 响应只需 69～182 ms，说明服务端快速返回了错误，没有开始传输 3.60～12.48 MiB 的 FBX 文件。

本项目后端识别到上游返回的是 JSON 而不是 FBX 后，将其转换成明确的本地错误：

```json
{
  "error": {
    "code": "MODEL_STORAGE_UNAVAILABLE",
    "message": "下载错误，请联系运维人员处理",
    "retryable": true
  }
}
```

对应 HTTP 状态为 `502 Bad Gateway`。因此，前端 Three.js/FBXLoader 从未收到可解析的 FBX 字节，无法显示 3D 模型。

**结论：当前故障不在前端渲染层，也不是文件过大造成的网络丢包。故障发生在上游 `/three-model-api` 的模型文件下载处理或其依赖的对象存储（文档标注为 MinIO）中。**

## 3. 正常请求链与故障位置

### 3.1 项目请求链

```text
浏览器 RemoteModelViewer
    │
    │ GET /api/model-showcase/:sceneId/model
    ▼
本项目 Express BFF（server.ts）
    │
    ├─ 1. GET /api/v1/three-model/models?model_id=<id>
    │      取得模型元数据、file_url、file_size
    │
    └─ 2. GET /api/v1/three-model/models/files?file_url=<URL编码后的对象key>
           预期取得 FBX 原始二进制
           │
           ▼
      上游模型下载处理 / MinIO 对象存储
```

### 3.2 已确认正常的链路

```text
浏览器 → 本项目 BFF                     正常
本项目 BFF → 上游 HTTP 服务             正常
上游模型元数据接口                       正常
上游模型文件列表接口                     正常
上游 Dashboard 接口                      正常
模型 ID → 文件元数据映射                 正常
```

### 3.3 已确认异常的链路

```text
上游文件下载处理 → 对象存储读取           异常
或
上游下载处理对存储结果的封装与响应         异常
```

故障边界已经缩小到上游文件下载接口内部。本项目无法从外部响应继续判断是对象不存在、存储连接失败、权限失败，还是下载处理程序自身抛出异常；需要上游运维结合服务端日志进一步确认。

## 4. 接口契约：预期与实际

### 4.1 文档规定的模型下载响应

请求：

```http
GET http://8.146.211.204:3100/three-model-api/api/v1/three-model/models/files?file_url=<encoded-object-key>
```

预期响应：

```http
HTTP/1.1 200 OK
Content-Type: application/octet-stream
Content-Disposition: inline; filename="<模型文件名>.fbx"
Content-Length: <与元数据 file_size 一致>

<FBX 原始二进制>
```

FBX 文件头应符合以下任意一种：

- 二进制 FBX：以 `Kaydara FBX Binary` 开头；
- ASCII FBX：忽略前导空白后以 `; FBX` 开头。

### 4.2 当前实际响应

```http
HTTP/1.1 200 OK
Content-Type: application/json
Content-Length: 95
Content-Disposition: <缺失>

{
    "code": -1,
    "data": {},
    "message": "下载错误，请联系运维人员处理"
}
```

### 4.3 契约偏差

| 检查项 | 预期 | 实际 | 判定 |
|---|---|---|---|
| HTTP 状态 | 成功才返回 200；下载失败应返回 4xx/5xx | 业务失败仍返回 200 | 不符合常规 HTTP 错误语义 |
| 业务 code | 二进制响应不使用 JSON 包装 | `-1` | 明确业务异常 |
| Content-Type | `application/octet-stream` | `application/json` | 错误正文，不是模型 |
| Content-Disposition | `inline; filename=...` | 缺失 | 未进入正常下载响应 |
| Content-Length | 应等于元数据文件大小 | 95 | 未传输模型 |
| Body | FBX 文件头及模型二进制 | JSON 错误信息 | 无法交给 FBXLoader |

HTTP 200 只能表示上游 HTTP 处理程序成功返回了一个响应，不能表示模型下载业务成功。`code=-1`、JSON 类型和错误消息共同证明下载业务失败。

## 6. 为什么不是“文件过大导致丢包”

### 6.1 最小文件同样失败

桥式起重机模型仅约 3.60 MiB，仍与 12.48 MiB 的污水泵模型返回完全相同的 95 字节错误。如果存在与文件大小相关的阈值，通常不会让不同大小文件以相同速度和相同业务消息全部失败。

### 6.2 服务端没有开始发送模型

下载接口在 69～182 ms 内返回 95 字节 JSON。模型二进制没有开始传输，因此不存在“传到一半丢包”或“大文件传输中断”的证据。

### 6.3 TCP 会处理普通网络丢包

HTTP/1.1 基于 TCP。普通链路丢包会由 TCP 重传，严重时通常表现为：

- 请求超时；
- 连接重置；
- socket 提前关闭；
- 响应正文少于 `Content-Length`；
- `fetch failed`、`ECONNRESET` 等传输错误。

当前实际表现是快速收到结构完整、长度一致、内容稳定的应用层 JSON 错误，符合服务端主动返回业务异常，不符合网络层随机丢包。

### 6.4 本项目上限没有触发

本项目后端设置的模型安全上限为 50 MiB。四个文件均小于此上限，且当前错误码不是 `MODEL_TOO_LARGE`，因此本地大小限制没有拦截请求。

## 7. 已排除或基本排除的原因

| 可能原因 | 判定 | 证据 |
|---|---|---|
| 前端窗口尺寸异常 | 排除 | 下载接口在进入 FBXLoader 前已经失败；窗口不会改变上游响应类型 |
| Three.js 不支持 FBX | 排除 | FBXLoader 尚未收到 FBX 字节；实际收到的是 JSON |
| FBX 文件解析异常 | 排除 | 没有可供解析的文件；错误发生在下载阶段 |
| 文件过大 | 基本排除 | 最大约 12.48 MiB，小于 50 MiB；最小约 3.60 MiB 同样失败 |
| 普通网络丢包 | 排除 | 快速收到完整、确定性的 95 字节 JSON 业务错误 |
| CORS | 排除 | 实际下载由 Node/Express 后端发起，不受浏览器 CORS 限制；直接测试结果相同 |
| HTTPS 混合内容 | 排除 | 浏览器只访问本地同源 BFF；BFF 到上游使用服务端 HTTP |
| 模型 ID 错误 | 排除 | 元数据、文件列表和 Dashboard 均能按四个 ID 正确返回 |
| 文件后缀不支持 | 排除 | 四个文件均为支持的 `.fbx` |
| 本地模型缓存损坏 | 排除 | 从未成功下载，未建立二进制缓存；直连上游也得到相同错误 |
| 本地 30 秒超时 | 排除 | 上游在 69～182 ms 内主动返回错误，没有触发超时 |
| 仅中文文件名编码问题 | 基本排除 | ASCII 文件名 `crane_08.fbx` 同样失败 |
| 单个对象损坏 | 基本排除 | 四个不同对象 key 全部返回相同错误，更像共享存储或下载处理故障 |

## 8. 最可能的上游内部原因

以下为根据外部证据给出的优先级排序。由于没有上游服务器、MinIO 控制台和服务日志权限，最终原因必须由上游运维确认。

### 8.1 对象存储不可达或存储客户端配置失效（优先级：最高）

可能包括：

- MinIO 服务停止、重启中或网络不可达；
- 下载服务使用的 MinIO endpoint、端口或 bucket 配置错误；
- 存储访问密钥过期、被替换或权限被回收；
- bucket policy 改动，应用账号失去读取权限；
- 下载服务与 MinIO 之间 DNS、路由或防火墙异常。

四个对象同时失败、但数据库中的文件元数据仍可读取，符合“数据库正常、对象存储访问失败”的典型表现。

### 8.2 数据库元数据存在，但对象已经丢失或迁移（优先级：高）

可能包括：

- 数据库保留了旧 `file_url`，实际对象已删除；
- 对象被迁移到新 bucket/prefix，元数据未同步；
- 存储清理任务误删对象；
- 恢复数据库备份后，数据库记录与对象存储版本不一致。

需要对四个对象 key 分别执行对象存在性检查。不能仅依据文件列表接口 `count=1` 判断对象真实存在，因为文件列表很可能读取的是数据库记录，而不是实时查询对象存储。

### 8.3 上游下载处理程序异常（优先级：中高）

同一路由根据 `model_id` 返回 JSON 文件列表，根据 `file_url` 返回二进制。可能存在：

- `file_url` 分支中的参数解析或 URL 解码异常；
- 路由分支选择错误；
- 存储异常被统一捕获后只返回“下载错误”；
- 流响应或文件名响应头构造时抛出异常；
- 框架升级后文件流响应方式不兼容。

由于 ASCII 文件名也失败，问题不应只归因于中文文件名编码。

### 8.4 上游文件记录与 bucket/prefix 约定不一致（优先级：中）

四个 key 都位于 `3d_model/2026-07-31/`。如果下载代码配置了不同 bucket，或在 key 前重复拼接了目录，所有对象都会查找失败。

### 8.5 上游资源保护或并发限制（优先级：低）

当前测试为低并发，且每次都快速返回相同业务错误，不像限流。若上游日志出现连接池耗尽、线程池拒绝或存储网关限流，再考虑此项。

## 9. 本项目当前保护与降级行为

### 9.1 后端保护

本项目 `server.ts` 已执行以下检查：

1. 场景 ID 必须属于四场景白名单；
2. 模型 ID 只从项目目录配置读取；
3. `file_url` 只从上游模型元数据读取，浏览器不能提交任意对象 key；
4. 只允许 FBX、GLB、GLTF；
5. 文件不得超过 50 MiB；
6. 下载超时为 30 秒；
7. 非超时错误最多请求 2 次；
8. JSON 错误不会被伪装成 FBX；
9. FBX/GLB/GLTF 文件头必须通过校验；
10. 首次成功的二进制在服务器运行期缓存；
11. 同一场景的并发下载会合并为一次请求。

当前响应被第 8 项识别，转换为：

```text
HTTP 502
code = MODEL_STORAGE_UNAVAILABLE
retryable = true
```

### 9.2 前端保护

前端 `RemoteModelViewer` 当前行为：

- 明确显示模型文件暂未显示及上游错误消息；
- 不把 JSON 交给 FBXLoader；
- 支持手动重新加载；
- 失败后每 30 秒自动重试；
- 模型异常不会让页面高度持续增长；
- 模型异常不会中断参数、图表、诊断和报告区域。

### 9.3 缓存状态

由于四个文件均未成功通过格式校验：

- 本项目后端不存在有效模型二进制运行期缓存；
- 浏览器不存在有效模型 `ArrayBuffer` 运行期缓存；
- 响应中没有 `X-Model-Runtime-Cache: HIT`；
- 每次模型重试仍需访问上游下载接口。

逐项确认：

- bucket 名称；
- 对象 key 完全一致；
- 大小与数据库 `file_size` 一致；
- 应用服务账号可执行读操作；
- 对象未处于归档、损坏或未完成上传状态。

### 10.3 检查存储连接配置

- endpoint、端口、协议是否正确；
- access key / secret key 是否有效；
- bucket 是否存在；
- 应用服务所在主机是否能访问存储 endpoint；
- 容器环境变量、配置中心和启动参数是否一致；
- 是否发生过 MinIO 迁移、bucket 改名或凭据轮换；
- 系统时间是否准确，避免 S3 签名时间偏差。

### 10.4 在上游服务器本机调用存储客户端

使用与下载服务相同的 endpoint、bucket 和凭据执行：

1. 对象 `stat/head`；
2. 下载前 32 字节；
3. 完整下载到临时目录；
4. 校验实际字节数；
5. 检查文件头。

如果存储客户端可以下载，而 HTTP API 仍失败，问题位于下载接口的参数处理、响应封装或异常处理；如果存储客户端也失败，则问题位于对象或存储连接。

### 10.5 修正 HTTP 错误语义

即使存储暂时不可用，上游也建议调整为：

- 成功下载：HTTP 200 + 二进制；
- 对象不存在：HTTP 404；
- 存储权限/服务异常：HTTP 502 或 503；
- 存储超时：HTTP 504；
- JSON 正文中保留可检索的错误码；
- 服务端日志记录原始异常，但响应中不泄露凭据和内部路径。

这可以避免调用方只看到 HTTP 200 而误判为成功。

### 17.3 为什么表现为“修改配色后才不显示”

本项目当前使用两级运行期缓存：

```text
浏览器 ArrayBuffer 缓存 → Node.js Buffer 缓存 → 上游模型下载服务
```

两级缓存都不是磁盘持久化缓存。若配色开发或部署期间发生以下任一情况：

- 开发服务重启；
- Node.js 进程重启；
- 浏览器页面整体重载；
- 新进程替换旧进程；

先前已经成功下载的缓存会被释放。新进程必须重新访问上游下载接口；如果此时上游存储服务再次异常，模型便会从“依靠旧缓存可显示”变为“无法重新取得文件”。

因此，配色修改与模型消失在时间上相邻，但本次后端 `502` 的直接原因仍是上游模型二进制下载失败。CSS 无法生成 `MODEL_STORAGE_UNAVAILABLE` 或 `UPSTREAM_TIMEOUT`。

### 17.4 同时发现的前端回归风险

上一轮全站配色扩展为了抬升大量历史黑底 Canvas，曾加入：

```css
mix-blend-mode: screen;
```

该规则会让 WebGL Canvas 进入额外的 GPU 合成层。外部模型视窗使用 `alpha: false` 的不透明 WebGLRenderer，不适合依赖屏幕混合改变背景；在部分显卡、浏览器或全屏状态下可能发生颜色失真、过度增亮或画布合成异常。

该规则不会造成本次接口 `502`，但确实是配色修改带来的显示回归风险，必须独立修复。
