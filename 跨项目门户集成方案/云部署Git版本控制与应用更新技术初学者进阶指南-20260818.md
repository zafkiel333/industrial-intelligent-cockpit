## 1. 先建立最重要的“五层模型”

初学者最容易把下面五件事当成同一件事：

```text
源代码 → Git 提交 → 构建产物 → 发布版本 → 正在运行的线上实例
```

它们有关系，但绝对不是同一东西。

### 1.1 源代码（Source Code）

源代码是人编写和维护的内容，例如：

```text
*.tsx / *.ts / *.vue / *.css
package.json
vite.config.ts
server.ts
配置模板和文档
```

源代码是“配方”，不一定是用户最终获取的东西。

### 1.2 Git 提交（Commit）

Git 提交是源代码在某个时刻的一次可追踪记录。

例如：

```text
b4ec6eb 页面跳转方法修改完成，现为页内跳转，已经部署并更新
```

`b4ec6eb` 是 commit ID 的缩写。完整 ID 是根据内容和历史计算出的标识。

一个 commit 能告诉你“源码当时是什么样”，但它不能单独证明：

- 代码构建成功了；
- 发布包是由这个 commit 构建的；
- 这个发布包已经上传；
- 服务器已经切换到它；
- 浏览器没有缓存旧产物。

### 1.3 构建产物（Build Artifact）

构建是把源代码处理成可交付形式的过程。

例如本项目：

```powershell
npm run build:all
```

会生成：

```text
dist-standalone/  场景库独立页产物
dist-microapp/    历史微应用兼容产物
```

里面主要是浏览器可直接加载的 HTML、CSS 和编译/压缩后的 JavaScript。

构建产物是“按照配方做出的成品”。

### 1.4 发布版本（Release）

发布版本是一个已准备交付的、应当不再原地修改的产物集合。

本项目的当前发布 ID：

```text
20260818-144540
```

它表示：

```text
2026-08-18 14:45:40 生成的发布包
```

它是时间戳版本，而不是语义化版本号。

### 1.5 部署实例（Deployment/Runtime）

部署是把某个发布版本安装到目标环境，并让真实流量访问它。

本项目当前线上运行指向：

```text
/nlplabProj/scene-library/current
  → /nlplabProj/scene-library/releases/20260818-144540
```

所以：

```text
发布包存在 ≠ 已经部署
已经部署 ≠ 已经验收
已经验收 ≠ 永远不会出问题
```

## 2. 从 Git 开始理解版本控制

### 2.1 版本控制解决什么问题

没有 Git 时，人们容易这样保存文件：

```text
项目-最终版.zip
项目-最终版2.zip
项目-真的最终版.zip
项目-最终版-修复.zip
```

这种方式不知道：

- 谁改了什么；
- 为什么改；
- 两份文件有什么区别；
- 哪一版上线了；
- 出错后应回到哪里；
- 多人修改时怎么合并。

Git 把项目历史组织成一个由 commit 连接起来的图。Git 官方文档将 commit 描述为项目历史中的一个步骤，分支和标签则是指向特定历史位置的名称引用。参见 [Git 官方文档](https://git-scm.com/docs/git)。

### 2.2 Git 的四个重要区域

```text
工作区 → 暂存区 → 本地仓库 → 远程仓库
```

#### 工作区（Working Tree）

你正在编辑的真实文件。

#### 暂存区（Index/Staging Area）

下一次 commit 准备收录的变更。

#### 本地仓库（Local Repository）

`.git` 目录中的完整历史。

#### 远程仓库（Remote Repository）

例如 GitHub、GitLab、Gitee 或公司自建 Git 服务器。用于协作和异地保存，但它不等于线上运行服务器。

### 2.3 一次规范提交的过程

```bash
git status --short
git diff
git add <本次确认需要提交的文件>
git diff --cached
git commit -m "feat: 增加场景库宿主导航协议"
```

每一步的意义：

| 命令 | 作用 |
|---|---|
| `git status` | 先看当前修改了什么 |
| `git diff` | 审查尚未暂存的内容 |
| `git add` | 只选中这一次提交要包含的文件 |
| `git diff --cached` | 在 commit 前再审查一遍 |
| `git commit` | 把当前暂存内容记录为一个历史节点 |

初学者应尽量避免不经检查就使用：

```bash
git add .
```

因为它可能把无关文件、本地配置、巨大产物甚至敏感文件一起放入提交。

### 2.4 分支是什么

分支可以理解为一条可独立向前开发的历史线。

```bash
git switch -c feature/scene-library-host-navigation
```

建议工作流：

```text
main（稳定主线）
 └─ feature/scene-library-host-navigation（功能分支）
      ├─ 开发
      ├─ 测试
      ├─ 代码审查
      └─ 合并回 main
```

不是所有项目都必须使用很复杂的 Git Flow。小团队可以使用“短生命周功能分支 + Pull Request + 快速合并”。关键不是分支多，而是：

- 主线是否可构建；
- 变更是否可审查；
- 测试是否自动执行；
- 哪个 commit 上线是否可追踪。

### 2.5 标签（Tag）是什么

分支会继续向前移动，标签通常用于固定指向一个发布节点。

```bash
git tag -a v0.2.0 -m "Scene library navigation release 0.2.0"
git push origin v0.2.0
```

标签像在历史地图上插一面旗子：

```text
这个 commit 对应 0.2.0 发布版本。
```

但 tag 仍然不是构建产物本身。专业发布还需把 tag/commit 与产物和校验值关联起来。

### 2.6 “撤销”不是只有一种

| 目标 | 常用工具 | 含义 |
|---|---|---|
| 放弃尚未提交的某文件修改 | `git restore <file>` | 修改将丢失，需谨慎 |
| 取消暂存 | `git restore --staged <file>` | 文件修改还在，只移出暂存区 |
| 公开历史中撤销某 commit | `git revert <commit>` | 新建一个反向 commit，适合已 push 的共享历史 |
| 移动本地分支指针 | `git reset` | 可改写本地历史，需明白 mixed/soft/hard 区别 |
| 临时收起未完成修改 | `git stash` | 不是正式发布或长期备份 |

初学者应特别警惕：

```bash
git reset --hard
git clean -fd
```

这些命令可能丢失未提交数据。不要因为“网上说这样能恢复干净”就在不理解目标时执行。

## 3. Git 不等于备份、发布或部署

### 3.1 Git 主要管源码历史

Git 适合：

- 源代码；
- 小型配置模板；
- 数据库迁移脚本；
- 基础设施代码；
- 测试和文档；
- 对变更做差异比较。

Git 通常不应直接保存：

- `node_modules/`；
- 每次可重新生成的大型构建目录；
- 服务器实时上传数据；
- 数据库数据文件；
- 用户上传内容；
- 密钥、密码和生产 `.env`；
- 巨大游戏原始素材和频繁变更的二进制文件。

大文件可考虑 Git LFS，大型游戏团队也可根据素材锁定、文件规模和编辑器工作流评估 Perforce 等系统。不要因为你“只了解 Git”就假设所有类型的产物都应放进普通 Git 仓库。

### 3.2 远程 Git 仓库不是线上服务器

```text
git push
```

只是把 commit 和分支/标签发送到远程 Git 服务。

它不自动意味着：

```text
npm run build
打包
上传到业务服务器
切换 current
重启 systemd
验证健康接口
```

只有配置 CI/CD 后，Git push/tag 才可能触发后续自动流程。

### 3.3 Git commit 信息不能替代发布记录

即使 commit 信息写了“已部署”，也应该有独立证据：

```text
发布 ID
Git commit ID
构建时间
产物 SHA-256
目标环境
操作人/流水线
健康检查结果
验收结果
上一可回滚版本
```

Git 提交记录是证据链的一环，不是全部。

## 4. 怎样给软件命名版本

### 4.1 时间戳版本

本项目当前使用：

```text
20260818-144540
```

优点：

- 不容易重复；
- 一眼可看出构建时间；
- 手工部署易理解；
- 目录按字符串排序基本等于按时间排序。

局限：

- 看不出是修复、新功能还是破坏性变更；
- 不能表达 API 兼容关系；
- 同一份源码重新构建会得到新时间戳；
- 如不记录 commit ID，仍无法确认对应源码。

### 4.2 语义化版本（SemVer）

语义化版本使用：

```text
MAJOR.MINOR.PATCH
主版本.次版本.修订版本
```

例如：

```text
1.4.2
```

官方规则的核心是：

- `MAJOR`：有不兼容的公共 API 变更；
- `MINOR`：新增向后兼容功能；
- `PATCH`：向后兼容的错误修复。

详见 [Semantic Versioning 2.0.0](https://semver.org/)。SemVer 还定义了预发布和构建元数据：

```text
1.5.0-alpha.1
1.5.0-rc.2
1.5.0+20260818.sha.b4ec6eb
```

需要注意：SemVer 首先要求项目明确自己的“公共 API”。对纯内部 Web 应用，也可以借用这种规则，但必须在团队内说清楚什么算兼容性变更。

### 4.3 版本号和构建号可以同时存在

推荐未来将三类标识同时保留：

```text
产品版本：0.2.0
发布 ID：20260818-144540
Git commit：b4ec6eb...
```

它们分别回答：

| 标识 | 回答的问题 |
|---|---|
| 产品版本 | 功能和兼容性处于什么阶段？ |
| 发布 ID | 这次产物什么时候构建/发布？ |
| Git commit | 精确由哪份源码生成？ |

### 4.4 已发布版本不应原地修改

一个重要的行业原则：

```text
同一版本标识应始终对应同一份内容。
```

如果 `20260818-144540` 已经发布，后来又修改了文件，应该生成一个新发布 ID，而不是静默替换旧包。

否则会出现：

```text
两台服务器都说自己运行 20260818-144540，
但实际文件不同。
```

这会破坏校验、审计和回滚。

## 5. 什么是构建，为什么不直接上传源码

### 5.1 前端构建做了什么

Vite 会完成诸多工作：

- 处理 TypeScript/TSX/Vue 等源码；
- 解析模块依赖；
- 把大量文件组织成浏览器可加载资源；
- 压缩 JavaScript/CSS；
- 处理图片和静态资源引用；
- 注入构建环境配置；
- 对资源文件名增加内容 hash，例如 `index-B7OWG8h6.js`；
- 生成最终 `index.html`。

文件名中的 hash 用于缓存破坏（cache busting）：内容变了，文件名也变，浏览器就不会把旧 JS 误当成新 JS。

### 5.2 本项目为什么有两份前端产物

```text
dist-standalone
dist-microapp
```

- `dist-standalone`：按 `/cockpit/` 路径独立运行；
- `dist-microapp`：按历史微应用路径 `/microapps/scene-library/` 构建。

当前主平台实际使用 iframe 加载 `dist-standalone`，不使用 qiankun。`dist-microapp` 仍在当前发布包中保留，是为了延续现有双产物发布结构，不代表当前 iframe 依赖它。

### 5.3 锁文件为什么重要

```text
package.json       描述允许的依赖范围和脚本
package-lock.json  记录精确解析的依赖树和校验信息
```

```bash
npm ci
```

专门适合在流水线和部署环境按锁文件安装。它不保证世界上任何时候都 100% 可重复，但比在服务器上随意 `npm install` 更可控。

### 5.4 构建成功不等于功能正确

构建成功只证明构建工具没有遇到阻断性错误。还需要：

- 单元测试；
- 类型检查；
- lint；
- 集成测试；
- 端到端测试；
- 安全扫描；
- 部署后健康检查；
- 真实浏览器验收。

本项目还有历史 TypeScript 非法字符问题，所以当前不能简单把全量 `tsc --noEmit` 当作唯一发布门禁。专业做法不是忽略问题，而是：

```text
明确记录已知基线问题
对本次变更做定向检查
保证 Vite 双构建通过
将历史问题单独安排治理
不把新错误与旧错误混为一谈
```

## 6. 发布包是什么

### 6.1 本项目的发布包

当前文件：

```text
scene-library-release-20260818-144540.tar.gz
```

它是 gzip 压缩的 tar 归档，主要包含：

```text
dist-standalone/
dist-microapp/
server.ts
package.json
package-lock.json
tsconfig.json
vite.config.ts
src/
```

它是“服务器部署包”，不是面向普通用户双击安装的 Windows/macOS/Android 安装包。

### 6.2 为什么不把 `node_modules` 打进当前包

当前流程是在服务器新 release 目录中执行 `npm ci`。

优点：

- 发布包较小；
- 依赖按 Linux 服务器平台安装；
- 避免把 Windows 本地的平台二进制依赖直接带到 Linux。

局限：

- 部署时依赖 npm registry/镜像站；
- 依赖安装增加时间和失败点；
- 原生依赖构建可能受系统工具链影响；
- 还需更严格地控制 registry、缓存和依赖供应链。

更成熟的方案可以在 CI 的 Linux 构建环境中完成所有依赖安装和测试，然后交付已验证的不可变产物或容器镜像。

### 6.3 SHA-256 校验值做什么

本次发布包上传前后使用 SHA-256 比对。

```text
本地文件 ──计算 SHA-256──┐
                               ├─ 一致：传输后内容相同
服务器文件 ─计算 SHA-256──┘
```

SHA-256 可以很强地检测内容是否改变，但“哈希一致”不自动证明发布者身份。如果攻击者能同时替换包和网页上的哈希，单纯哈希不足以建立信任。

更高级的信任链还包括：

- 代码签名；
- 产物签名；
- 保护 CI 密钥；
- 受保护的发布分支/标签；
- 产物库权限；
- SBOM（软件物料清单）；
- 供应链证明/签署。

## 7. 什么是云部署

### 7.1 云服务器不是一种神秘新电脑

对本项目而言，云服务器可以简单理解为：

```text
运行在云厂商数据中心的 Ubuntu Linux 计算机，
有公网 IP、磁盘、内存、网络和进程。
```

与自己电脑的核心区别是：

- 通常 24 小时对外服务；
- 有公网/内网地址；
- 需要安全组、防火墙和 SSH 运维；
- 需要进程托管、日志、监控和备份；
- 不应依赖某个人一直打开终端窗口。

### 7.2 部署的本质

部署本质上是：

```text
把已验证的产物放到目标环境
→ 配置它依赖的运行环境
→ 让流量切换到新版本
→ 验证新版本
→ 失败时恢复旧版本
```

专业部署不是：

```text
把一堆文件拖到服务器，然后祈祷它可以运行。
```

### 7.3 常见环境

| 环境 | 用途 |
|---|---|
| local | 开发者自己电脑 |
| development | 共享开发联调 |
| test/QA | 功能、回归、集成测试 |
| staging/pre-production | 尽可能接近生产的预发布环境 |
| production | 真实用户访问的生产环境 |

小项目可能暂时只有本地和一台线上服务器，但也应该理解环境隔离的价值。直接在生产上试验，会把开发风险直接转化为用户故障。

## 8. 本项目的真实云端拓扑

```text
用户浏览器
    │
    │  http://47.122.104.52:8081/cockpit/
    ▼
Nginx（公网 8081）
    ├─ /cockpit/                 → dist-standalone 静态文件
    ├─ /microapps/scene-library/ → dist-microapp 静态文件
    └─ /scene-library-api/       → 127.0.0.1:3102/api/
                                             │
                                             ▼
                                  Express / Node.js 后端
                                  scene-library.service
```

主平台在另一台服务器：

```text
http://8.146.211.204:3100
    └─ /scene-library 页使用 iframe
       加载 http://47.122.104.52:8081/cockpit/
```

### 8.1 为什么 Nginx 在外层

Nginx 适合：

- 快速提供 HTML/CSS/JS/图片；
- 处理路径映射；
- 反向代理 API；
- 配置缓存响应头；
- 终止 TLS/HTTPS；
- 限制请求体大小和超时；
- 作为应用服务前的稳定入口。

不建议让 Vite dev server 或 Express 直接承担所有公网静态资源和 TLS 职责。

### 8.2 为什么 Express 只监听 `127.0.0.1:3102`

```text
127.0.0.1
```

只代表本机回环地址。外部用户不能直接连接 `3102`，而是通过 Nginx 公开的 `8081` 路径访问。

优点：

- 缩小公网攻击面；
- 统一由 Nginx 管理入口；
- 后端无需自己直接暴露公网端口；
- 将代理、超时和日志策略集中在 Nginx。

云安全组也不应对公网放行 `3102`。

### 8.3 systemd 做什么

`scene-library.service` 是 systemd 服务单元。它负责：

- 开机启动；
- 按指定用户运行；
- 设置工作目录；
- 加载环境变量；
- 进程异常后重启；
- 向 journal 收集标准输出/错误；
- 向运维提供统一的 `start/stop/restart/status`。

它避免这种脆弱运行方式：

```text
运维人员 SSH 登录
→ 手动 npm start
→ 关闭终端后进程也没了
```

## 9. 本项目的发布目录为什么这样设计

```text
/nlplabProj/scene-library/
├─ releases/
│  ├─ 20260817-154326/
│  └─ 20260818-144540/
├─ current  → releases/20260818-144540
├─ previous → releases/20260817-154326
├─ shared/
│  ├─ data/
│  ├─ model-cache/
│  └─ npm-cache/
└─ www/
   ├─ cockpit → current/dist-standalone
   └─ microapps/scene-library → current/dist-microapp
```

### 9.1 `releases/`：每个版本独立安装

新版本不覆盖旧版本，而是放到新目录。

好处：

- 新版本可以先解压和安装依赖，不影响当前线上；
- 可以在切换前检查文件和协议标记；
- 回滚时旧版本仍存在；
- 不会出现一半新文件、一半旧文件。

### 9.2 `current`：当前线上指针

`current` 是软链接，类似 Windows 快捷方式，但是文件系统层面的路径引用。

```text
current → releases/20260818-144540
```

systemd 和 Nginx 不需要每次都改成新时间戳路径，它们只跟随 `current`。

### 9.3 `previous`：显式记录上一可回滚版本

在切换新版本前：

```text
previous → 当前旧版本
```

如新版本失败，可以快速把 `current` 重新指向 `previous`。

更成熟的系统会保留多个发布历史，并根据空间和合规政策清理，而不是只依赖一个 `previous`。

### 9.4 `shared`：不随发布切换的持久数据

用户上传数据、模型缓存等不能放在某个 release 目录中，否则：

```text
回滚代码 = 一起回滚/丢失了新用户数据
```

正确边界是：

```text
代码和静态产物 → releases
持久业务数据       → shared 或独立数据库/对象存储
```

## 10. 从本地到云端的完整流程

### 10.1 阶段 A：确认源码状态

```powershell
git status --short
git branch --show-current
git log -1 --oneline
git diff --check
```

目的：

- 知道当前分支和 commit；
- 区分本次变更和用户其他未提交变更；
- 不把无关文件意外打进版本；
- 审查空白和冲突标记问题。

### 10.2 阶段 B：测试和构建

```powershell
npm run build:all
```

当前会顺序构建：

```text
npm run build:standalone
npm run build:microapp
```

应检查：

- 进程退出码为 0；
- 两份 `index.html`/入口文件存在；
- 资源 base path 正确；
- 本次新增协议字符出现在构建产物中；
- 只有已知的大 bundle 警告，没有新构建错误。

### 10.3 阶段 C：生成不可变发布包

用新的 release ID 创建：

```text
scene-library-release-<RELEASE_ID>.tar.gz
```

然后记录：

```text
文件名
文件大小
SHA-256
Git commit
构建机环境
Node/npm 版本
构建命令
```

### 10.4 阶段 D：上传到云服务器临时区

```powershell
scp "./scene-library-release-<RELEASE_ID>.tar.gz" `
  root@47.122.104.52:/tmp/scene-library-release-<RELEASE_ID>.tar.gz
```

`/tmp` 是中转区，不是正式运行目录。

上传后在服务器计算 SHA-256，必须和本地一致。如不一致，不得解压和切换。

### 10.5 阶段 E：安装到新 release 目录，但不切流量

```text
创建 releases/<RELEASE_ID>
→ 解压
→ 校验关键文件
→ 设置正确用户/组
→ npm ci
→ 检查 tsx 可执行
→ 检查构建产物标记
```

这一阶段不改 `current`，所以新版本即使安装依赖失败，用户仍在使用旧版本。

### 10.6 阶段 F：切换前检查

至少检查：

```text
current 仍指向预期旧版本
新 release 文件完整
依赖已安装
Nginx 配置语法正确
当前服务 active
当前健康接口正常
回滚目标明确
```

### 10.7 阶段 G：原子切换

简化过程：

```text
previous → 旧 current 真实版本
更新 APP_VERSION
current  → 新 release
重启 scene-library.service
```

“原子”的意思不是整个业务世界在一个 CPU 指令里完成，而是用户视角下尽量不看到“文件正在一个个覆盖”的中间状态。

软链接改指向很快，但 Node 后端进程仍需要重启才会使用新工作目录和代码。

### 10.8 阶段 H：部署后验证

```text
systemd 服务 active
3102 只监听 127.0.0.1
内部 API 健康接口版本正确
Nginx 8081 公开健康接口正确
/cockpit/ 返回 200
当前 HTML 引用新 hash JS
微应用入口返回 200
核心功能浏览器验收通过
Nginx/systemd 日志无新错误
```

## 11. 为什么能快速回滚

### 11.1 代码回滚的简化流程

```text
新版本验证失败
  → current 重新指向 previous
  → 恢复旧环境版本标识
  → 重启 scene-library.service
  → 重新验证
```

因为旧 release 目录没有被覆盖，回滚不需要重新从 Git 构建一次。

### 11.2 代码回滚不等于数据回滚

如新版本已经：

- 改变了数据库结构；
- 写入了不兼容数据；
- 删除了业务数据；
- 执行了不可逆外部操作；

单纯切回旧代码不能恢复这些数据。

专业团队会单独设计：

- 向前兼容的数据库迁移；
- expand/contract 迁移策略；
- 备份和恢复演练；
- 双写/兼容窗口；
- 不可逆操作审批；
- 幂等和补偿逻辑。

本项目当前将场景数据和模型缓存放在 `shared` 目录，使代码版本切换不覆盖持久数据。这是正确的基础分离，但不能替代正式备份。

### 11.3 什么是回滚演练

不要等生产出事时才第一次试回滚。

演练应验证：

- 旧产物真的保留；
- 软链接切换命令正确；
- 环境配置能恢复；
- 服务能重启；
- 健康检查会报旧版本；
- 用户业务能恢复；
- 回滚时间是否满足目标。

## 12. 环境变量、密钥和配置

### 12.1 为什么配置不全部写死在代码中

不同环境可能需要：

```text
不同端口
不同 API 地址
不同数据目录
不同缓存目录
不同日志级别
不同功能开关
不同密钥
```

如果都写死在源码中，为了更换一个端口就要改代码和重新构建。

### 12.2 本项目的运行配置

systemd 从：

```text
/etc/scene-library-next.env
```

加载运行环境变量，例如：

```text
NODE_ENV=production
HOST=127.0.0.1
PORT=3102
APP_VERSION=20260818-144540
SCENE_DATA_DIRECTORY=/nlplabProj/scene-library/shared/data
MODEL_CACHE_DIRECTORY=/nlplabProj/scene-library/shared/model-cache
```

生产环境文件不应直接提交到 Git，应限制文件权限、记录变更并对密钥使用专门的 secrets manager/密钥管理。

### 12.3 前端环境变量并不秘密

很多初学者认为：

```text
只要叫 VITE_SECRET_KEY，它就是秘密。
```

这是错误的。

构建到浏览器 JavaScript 中的值，最终用户通常都能查看。真正的服务端密钥不得通过 Vite 变量打进前端产物。

## 13. 缓存：为什么已发布却看到旧页面

### 13.1 浏览器缓存的价值

每次都重新下载十几 MB JavaScript 会很慢，所以浏览器会缓存资源。

理想策略：

```text
index.html：短缓存或 no-cache，便于及时发现新资源名
hash 静态资源：长期强缓存，因为内容变化后文件名也变
```

### 13.2 为什么不要每次使用同一个 `app.js`

如文件始终叫：

```text
app.js
```

中间 CDN、代理或浏览器可能继续使用旧内容。

内容 hash 文件：

```text
index-B7OWG8h6.js
```

把文件内容和 URL 绑定在一起。

### 13.3 Service Worker/PWA 会让缓存更强

PWA 可用 Service Worker 在浏览器与网络之间拦截请求、实现离线缓存和后台能力。参见 [MDN Service Worker API](https://developer.mozilla.org/en-US/docs/Web/API/Service_Worker_API)。

但 Service Worker 也带来更复杂的更新生命周期：

- 新 Service Worker 下载不代表立即接管；
- 旧页面可能仍由旧 Worker 控制；
- 缓存版本管理错误可导致长时间使用旧页面；
- 必须设计激活、刷新提示和缓存清理策略。

本项目当前的主要发布模型是 Nginx + 带 hash 静态资源，不要在没有需求时为了“显得高级”随意增加 Service Worker。

## 14. 监控、日志和健康检查

### 14.1 健康检查不是完整业务测试

```text
/scene-library-api/health
```

返回：

```json
{"status":"ok","version":"20260818-144540"}
```

说明：

- 请求到达了相应服务；
- Express 能返回响应；
- 当前运行版本标识是预期值。

它不能单独证明：

- 所有业务 API 都正常；
- 上游模型库正常；
- 浏览器 JavaScript 没有错误；
- iframe 跨项目通信已完成；
- 所有用户权限正确。

### 14.2 需要看哪些日志

```bash
systemctl status scene-library.service --no-pager -l
journalctl -u scene-library.service -n 100 --no-pager -l
tail -n 100 /var/log/nginx/error.log
tail -n 100 /var/log/nginx/access.log
```

应该理解：

- 应用日志记录业务/运行异常；
- Nginx access log 记录请求；
- Nginx error log 记录代理、文件和网络错误；
- 浏览器 Console 记录前端运行错误；
- 浏览器 Network 可显示请求 URL、状态码、响应头和资源版本。

专业系统会进一步建立：

- 指标（延迟、错误率、流量、资源使用）；
- 分布式追踪；
- 结构化日志；
- 请求 ID；
- 告警；
- SLI/SLO；
- 发布事件标记。

### 14.3 发布时需要关注的四大黄金信号

```text
延迟（Latency）
流量（Traffic）
错误（Errors）
饱和度（Saturation）
```

初学者不需要立即搭建完整可观测平台，但要开始用“有证据地判断发布是否正常”取代“页面看起来能打开”。

## 15. SSH、密码和密钥

### 15.1 SSH 做什么

SSH 用于：

- 加密连接 Linux 服务器；
- 远程执行命令；
- 使用 scp/sftp 传输文件；
- 使用公钥完成身份验证。

### 15.2 密码登录和密钥登录的区别

| 方式 | 优点 | 风险/局限 |
|---|---|---|
| 密码 | 初始简单 | 容易被爆破，自动化困难，密码共享难审计 |
| SSH 密钥 | 适合自动化，可独立撤销 | 私钥泄漏即可能失陷，需权限、口令和密钥管理 |

本次为了减少重复输入密码，创建了专用 SSH 密钥。但“无口令 root 私钥”便利与风险同时存在。更成熟的生产做法应包括：

- 不直接长期使用 root；
- 为部署创建专用低权限账号；
- 仅授予必需 sudo 命令；
- 私钥使用强口令并由 ssh-agent/密钥管理器缓存；
- 为每个人/流水线使用独立密钥；
- 人员离开或设备丢失时立即撤销公钥；
- 限制来源 IP、使用跳板机/VPN；
- 审计 SSH 登录和 sudo 操作；
- 由 CI/CD 使用短期凭据或受保护密钥完成部署。

## 16. 本项目手工发布方式的优点和不足

### 16.1 已经做对的地方

- 有明确 release ID；
- 发布包上传后校验 SHA-256；
- 新版本在独立目录安装；
- 不在正在运行的目录中逐文件覆盖；
- 使用 `current`/`previous` 软链接；
- 持久数据与代码 release 分离；
- 后端仅监听回环地址；
- systemd 托管进程；
- Nginx 提供统一公网入口；
- 切换前和切换后都有健康检查；
- 失败脚本可自动恢复旧指向。

### 16.2 仍可以改进的地方

- 发布包和 Git commit 尚缺标准化 manifest 关联；
- 时间戳版本没有表达功能/API 兼容语义；
- 依赖在生产服务器上安装；
- 发布步骤仍依赖人工复制命令；
- 开发、测试、预发布和生产环境边界还可加强；
- 全量 typecheck 有历史阻断项；
- 产物签名、SBOM 和供应链证明尚未建立；
- 可观测性主要依赖手工 curl 和日志；
- SSH root 运维权限过大；
- 主平台与场景库版本尚未建立自动兼容矩阵。

这些不是说当前发布“不能用”，而是一条从可用、可回滚，逐步走向可重复、可审计、可自动化的成熟度路径。

## 17. Web 站点发布与“安装包”的本质区别

### 17.1 Web 应用：代码主要部署在服务器

用户打开网址时，浏览器从服务器下载 HTML/CSS/JS。

```text
开发者发布服务器新版本
          ↓
用户下次打开/刷新网页
          ↓
浏览器获取新 HTML 和新 hash 资源
```

用户通常不需要下载一个安装程序并点击“下一步”。

### 17.2 原生应用：代码已安装到用户设备

Windows/macOS/Linux/Android/iOS 原生或打包应用的可执行代码存在用户设备上。

发布者不能像 Web 一样只切换服务器软链接就让所有用户立即运行新代码。需要：

```text
为目标操作系统/架构构建
→ 打包
→ 签名
→ 上传应用商店或更新服务器
→ 审核/发布
→ 用户设备检测新版本
→ 下载和安装
→ 必要时重启应用
```

### 17.3 服务端回滚与客户端回滚的巨大区别

服务端：

```text
运维可以统一把所有流量切回旧版本。
```

客户端：

```text
用户设备可能分散在全世界，
处于多个版本，有的离线，有的禁止自动更新。
```

因此客户端系统必须更强调：

- 向后兼容 API；
- 最低支持版本；
- 强制/可选更新；
- 多版本并存；
- 数据迁移；
- 更新失败恢复；
- 分批发布；
- 应用商店审核和签名。

## 18. Windows、macOS 和 Linux 桌面应用的发布/更新

### 18.1 Windows 常见包形式

| 形式 | 简介 |
|---|---|
| `.exe` 安装器 | 可由 NSIS、Inno Setup、Squirrel 等工具生成 |
| `.msi` | Windows Installer 数据库式安装包，常用于企业部署 |
| `.msix`/`.msixbundle` | 现代 Windows 打包格式，有 manifest、签名和管理化更新 |
| portable ZIP | 解压即用，但开始菜单、卸载、升级和权限需自己处理 |

MSIX 会在包中保存文件块哈希信息，Windows 可比较旧包和新包并只获取已变化块。官方文档介绍了基于 `AppxBlockMap.xml` 的 64KB 块级差分更新，参见 [Microsoft MSIX 差分更新](https://learn.microsoft.com/en-us/windows/msix/desktop/managing-your-msix-deployment-update)。

### 18.2 macOS 常见形式

| 形式 | 简介 |
|---|---|
| `.app` | macOS 应用 Bundle，实际是有规定目录结构的包 |
| `.dmg` | 磁盘映像，常用于拖拽安装 `.app` |
| `.pkg` | 安装器包，可安装到多个系统位置 |
| Mac App Store | 由商店进行审核和分发 |

直接网站分发的 macOS 应用通常需要 Developer ID 签名和 notarization（公证），否则会触发系统安全警告或阻止。

### 18.3 Linux 常见形式

```text
.deb / apt
.rpm / dnf/yum
AppImage
Flatpak
Snap
发行版软件仓库
tar.gz
```

Linux 应用更新往往由发行版包管理器、Flatpak/Snap 商店或应用自己的更新器完成。

### 18.4 Electron 应用

Electron 把 Chromium + Node.js + Web 资源打包成桌面应用。

它的发布链路是：

```text
Web/Node 源码
→ Electron 打包
→ 按 Windows/macOS/Linux 和 CPU 架构生成产物
→ 代码签名
→ 发布安装包和更新元数据
```

Electron 官方 `autoUpdater` 在 macOS/Windows 上使用相应更新机制，可从更新源获取元数据、下载新版本并重启安装。Electron 官方还说明内置 autoUpdater 不直接支持 Linux，Linux 通常由发行包管理器更新。参见 [Electron 更新指南](https://www.electronjs.org/docs/latest/tutorial/updates) 和 [`autoUpdater` API](https://www.electronjs.org/docs/latest/api/auto-updater/)。

### 18.5 Tauri 应用

Tauri 通常使用系统 WebView + Rust 后端，产物体积常比捆绑 Chromium 的 Electron 小，但具体取决于功能和资源。

Tauri v2 更新器要求更新产物签名，更新元数据包含版本、URL 和签名，生产模式默认要求 TLS。参见 [Tauri Updater 官方文档](https://v2.tauri.app/plugin/updater/)。

### 18.6 桌面应用为什么需要代码签名

哈希回答：

```text
文件有没有改变？
```

数字签名还能帮助回答：

```text
这份包是否由拥有对应私钥的发布者签发？
```

操作系统和更新器会检查签名。私钥丢失可能导致无法继续向现有用户发布被信任的更新，因此签名密钥是极高价值资产。

## 19. Android 应用安装和更新

### 19.1 APK 和 AAB 不是同一个东西

| 格式 | 作用 |
|---|---|
| APK | Android 设备实际安装的包 |
| AAB | 发布到 Google Play 的应用束格式，不是普通设备直接安装包 |

Google Play 可根据设备的 CPU、屏幕密度、语言等，从 AAB 生成针对设备的优化 APK，减少用户下载不需要的资源。参见 [Android App Bundle 官方说明](https://developer.android.com/guide/app-bundle)。

### 19.2 Android 更新必须满足的核心条件

一般情况下，要覆盖安装现有 App，新版本需要：

- 相同 application ID；
- 匹配的签名证书，或有效的密钥轮换证明；
- 满足版本代码升级要求；
- 符合目标用户/设备条件。

详见 [Android 官方：App 更新如何工作](https://developer.android.com/google/play/app-updates)。

如果签名不一致，系统通常不会把它当作同一应用的正常更新。

### 19.3 灰度、测试轨道和应用内更新提示

Google Play 可配置内部测试、封闭/开放测试和生产发布轨道。应用内更新 API 支持：

- Flexible：用户继续使用时后台下载；
- Immediate：全屏更新流程，需更新并重启后继续。

参见 [Android In-app Updates](https://developer.android.com/guide/playcore/in-app-updates)。

### 19.4 大型 Android 游戏资源

Google Play 提供 Play Asset Delivery，可将大型资源包按不同模式交付：

- install-time：安装时；
- fast-follow：安装后快速继续下载；
- on-demand：应用运行时按需下载。

这样可以把首次安装所必须的代码/资源与后续地图、高清素材、语音包等分开。参见 [Android App Bundle 格式与 Asset Pack](https://developer.android.com/guide/app-bundle/app-bundle-format)。

### 19.5 “热更新”不能绕过平台规则

手机 App 可以从服务器更新：

- JSON 配置；
- 文案；
- 图片/音视频；
- 游戏关卡数据；
- 模型/资源包；
- 功能开关；
- 服务器驱动的业务内容。

但不能简单将“下载新可执行代码绕过应用商店”视为普遍合法且可靠的方案。必须区分：

```text
内容更新
配置更新
WebView 远程页面更新
解释执行脚本
原生可执行代码更新
```

并根据 Google Play/其他应用市场政策、安全模型和所在地区要求审查。

## 20. iOS/iPadOS 应用安装和更新

### 20.1 基本链路

```text
Xcode 构建 Archive
→ 签名和 provisioning
→ 验证
→ 上传 App Store Connect
→ TestFlight 测试
→ App Review
→ App Store 发布
```

Apple 官方建议先生成 Archive，使用 TestFlight 给测试人员分发构建，然后提交审核和发布。参见 [Apple：分发 beta 和正式版本](https://developer.apple.com/documentation/xcode/distributing-your-app-for-beta-testing-and-releases/)。

### 20.2 TestFlight 是什么

TestFlight 是 Apple 的 beta 分发系统，用于：

- 管理内部/外部测试人员；
- 分发测试构建；
- 收集反馈和崩溃信息；
- 在正式审核前验证 release build。

它不是 Git 仓库，也不是生产应用商店本身。参见 [TestFlight Overview](https://developer.apple.com/help/app-store-connect/test-a-beta-version/testflight-overview/)。

### 20.3 分阶段发布

Apple App Store 支持将自动更新分 7 天逐步发布给部分用户，并允许暂停分阶段发布。这是一种平台级灰度能力。参见 [Apple 分阶段发布版本更新](https://developer.apple.com/help/app-store-connect/update-your-app/release-a-version-update-in-phases)。

需注意：即使开启分阶段自动更新，用户仍可能手动下载已发布版本。因此灰度不是绝对隔离，仍需要后端兼容、监控和功能开关。

### 20.4 iOS 的远程内容与二进制更新

和 Android 类似，iOS App 可以从服务器获取内容、配置和资源，但应用二进制、可执行代码和解释执行能力受到签名、审核和平台政策约束。

专业做法是在设计“热更新”前明确：

- 更新的是数据、资源还是代码；
- 是否改变 App 的核心行为；
- 是否符合当前 App Store Review Guidelines；
- 是否有签名、完整性校验和回滚；
- 是否会导致审核版本与用户实际运行功能显著不同。

## 21. 游戏安装包和更新包为什么看起来不一样

### 21.1 游戏通常比一般 App 大得多

大容量往往来自：

- 纹理；
- 模型；
- 音频；
- 过场动画；
- 地图；
- 多语言语音；
- shader 和平台专用资源；
- 引擎运行时；
- 可执行代码和反作弊组件。

如每次改一张图都让用户重新下载 100GB，成本和体验都无法接受。

### 21.2 完整包、差分包和分块更新

#### 完整包

包含新版本所有文件。

优点：简单，从任意老版本都可安装。  
缺点：大，重复下载未变内容。

#### 文件级更新

哪个文件变了就下载哪个整文件。

缺点：如一个 20GB 大包文件只改了少量内容，仍可能需重下整个文件。

#### 二进制差分（Binary Diff）

计算旧文件到新文件的变换。

优点：可很小。  
缺点：可能对起始版本敏感，安装需更多 CPU/磁盘，中断恢复和多版本路径复杂。

#### 内容寻址分块（Content-addressed Chunks）

把文件分成块，每块按内容哈希标识。新旧版本共用的块不重新下载，只下载新块。

优点：

- 跨版本复用；
- CDN 缓存友好；
- 可并行下载；
- 便于断点续传和校验；
- 可实现修复/验证文件。

局限：

- 需要 manifest、块存储、缓存和 GC；
- 打包格式不合理会造成块大面积变化；
- 下载量小不代表安装快，大量磁盘重写仍可能很慢。

### 21.3 SteamPipe 作为具体例子

SteamPipe 会将文件分成约 1MB 的块，压缩和加密后上传；更新时尽量复用与旧 build 相同的块，只下载新/已变化块。每个 depot 会生成 manifest，整个应用构建有 BuildID，并可切换公开或 beta 分支和回滚 build。参见 [SteamPipe 官方文档](https://partner.steamgames.com/doc/sdk/uploading?l=english)。

官方文档也特别提醒：如果引擎的 pack 文件因为一个小修改就让后续大量数据偏移，会使本应较小的更新变得很大。

这个知识非常重要：

```text
更新包大小不只取决于“改了多少逻辑”，
还取决于资源怎么打包、排列和分块。
```

### 21.4 游戏启动器通常做什么

```text
获取最新 manifest
→ 比较本地版本/块
→ 估算下载和磁盘空间
→ 从 CDN 并发下载
→ 验证哈希/签名
→ 解压/重建 pack
→ 写入临时目录
→ 安全切换
→ 失败时恢复
→ 启动游戏
```

所以游戏“下载 2GB，安装却等待很久”不一定是网速问题，可能是解压、校验、重写大包和磁盘 I/O。

### 21.5 游戏中的“热更新”

可能包括：

- 远程配置；
- 活动数据；
- 脚本；
- AssetBundle/Pak/资源包；
- 地图、角色和音频；
- shader 变体；
- DLC；
- 修复包；
- 服务端规则。

需区分：

```text
服务端逻辑更新：玩家无需更新客户端，但客户端协议必须兼容
客户端资源更新：下载新内容，不一定改可执行文件
客户端代码更新：通常需平台补丁/商店审核/签名
```

手机和主机平台还需遵守各自的审核、包大小、签名和可执行代码政策。

## 22. 容器镜像和 Kubernetes 与本项目方式的区别

### 22.1 容器镜像是什么

可把容器镜像理解为：

```text
应用文件
+ 运行时和系统依赖
+ 启动参数和默认配置
+ 按层组织的不可变文件系统
```

OCI 镜像由 manifest、配置和文件系统 layers 等组成，描述符按 digest 引用内容。后续层表示相对父层的文件添加、修改和删除。参见 [OCI Image Specification](https://specs.opencontainers.org/image-spec/?v=v1.1.1) 和 [OCI Layer Specification](https://specs.opencontainers.org/image-spec/layer/)。

### 22.2 容器镜像和 tar.gz 发布包对比

| 方面 | 本项目 tar + 主机运行 | OCI 容器镜像 |
|---|---|---|
| 运行环境 | 依赖主机 Node/npm/systemd | 运行时和应用依赖多数封装在镜像 |
| 产物 | tar.gz + 服务器安装依赖 | 分层、带 manifest/digest 的镜像 |
| 分发 | scp 到服务器 | push/pull 镜像仓库 |
| 启动 | systemd 直接运行 Node | 容器运行时启动镜像 |
| 隔离 | 主机进程和文件权限 | namespace/cgroup/容器文件系统 |
| 回滚 | 切软链接 + 重启 | 把 workload 改回旧镜像 digest/tag |

容器不是自动安全，也不是不需运维。它只是提供更标准的打包和运行边界。仍需：

- 漏洞扫描；
- 基础镜像更新；
- 密钥管理；
- 最小权限；
- 日志和监控；
- 持久存储；
- 网络和入口；
- 备份回复。

### 22.3 Kubernetes 做什么

Kubernetes 不是用来写业务代码的，它是容器编排系统，帮助管理：

- 容器副本；
- 调度；
- 健康检查；
- 服务发现；
- 滚动更新；
- 回滚；
- 扩缩容；
- ConfigMap/Secret；
- 存储和网络对象。

Kubernetes Deployment 可通过新旧 ReplicaSet 逐步替换 Pod，并保留 revision history 以支持 `kubectl rollout undo`。参见 [Kubernetes 滚动更新和回滚](https://kubernetes.io/docs/tasks/run-application/update-deployment-rolling/)。

### 22.4 现在是否应该立即把本项目改成 Kubernetes

不一定。

如果只有一台服务器、一个 Node 后端和 Nginx，当前 release 目录 + systemd 方案比较容易理解和维护。

在以下情况出现时，容器/编排的价值会提高：

- 多服务、多副本；
- 多环境一致性难保证；
- 需要自动扩缩容；
- 需要跨节点调度和故障转移；
- 已有成熟平台团队；
- 需要标准镜像供应链和自动发布。

不要把“用了 Kubernetes”当作技术水平的证明。专业能力体现在是否能根据复杂度、人力和可靠性目标选择合适工具。

## 23. Web、桌面、移动、游戏、容器的统一对比

| 类型 | 代码主要在哪 | 产物 | 常见更新方式 | 谁控制切换 | 回滚难度 |
|---|---|---|---|---|---|
| Web 站点 | 服务器 + 浏览器临时下载 | HTML/CSS/JS + 后端 | 部署服务器，用户刷新 | 运维/平台 | 通常较容易统一回滚 |
| Windows 桌面 | 用户电脑 | EXE/MSI/MSIX | 商店、包管理、自更新 | 商店/更新器/用户 | 多版本并存，较复杂 |
| macOS 桌面 | 用户 Mac | APP/DMG/PKG | App Store 或签名自更新 | Apple/更新器/用户 | 受签名和公证约束 |
| Linux 桌面 | 用户设备 | DEB/RPM/AppImage/容器包 | 发行版仓库或自更新 | 包管理器/用户 | 分发版差异较大 |
| Android | 用户手机 | APK，Play 发布 AAB | 应用市场/企业分发 | Google Play/市场/用户 | 签名+版本+分批，多版本 |
| iOS | 用户设备 | 签名 App/IPA 分发产物 | TestFlight/App Store/MDM | Apple/企业管理/用户 | 审核与签名限制强 |
| PC 游戏 | 用户电脑 | 平台 build/depot/manifest/chunks | Steam/Epic/自有 launcher | 平台/发行商 | 需兼容存档和大资源 |
| 容器服务 | 云/集群 | OCI image | 拉取新镜像、滚动更新 | 编排器/平台 | 代码回滚易，数据仍难 |

它们共同的核心问题是：

```text
我当前是什么版本？
服务器有什么新版本？
我需要下载哪些内容？
怎样证明下载内容正确且可信？
安装中断怎么恢复？
新版本出错怎么回去？
新旧客户端和服务端如何兼容？
```

不同技术只是在不同平台约束下回答这些问题。

## 24. 版本兼容：真正的高阶难题

### 24.1 不要只问“是不是最新版”

更重要的是：

```text
场景库版本 A 能否与主平台版本 B 通信？
前端版本 C 能否调用后端 API 版本 D？
老手机客户端能否继续连接新服务器？
新代码写入的数据能否被旧代码读取？
```

### 24.2 协议版本

本项目的跨项目导航使用：

```text
protocolVersion = 1.0
```

这与场景库发布 ID 不是同一概念。

```text
场景库发布 ID：这次部署是哪一版
协议版本：      两个系统以什么消息格式对话
```

以后如果只增加可选字段，可能仍兼容 1.0；如果删除必要字段或改变含义，可能需要新协议版本并提供过渡期。

### 24.3 扩展—兼容—收缩（Expand and Contract）

一种成熟升级思路：

```text
1. 先增加新字段/新接口，保留旧的
2. 新旧两端都兼容一段时间
3. 观测旧版本使用量
4. 所有调用方完成迁移
5. 再删除旧字段/旧接口
```

这比同时上线两端并期望“一秒都不差”更可靠。

### 24.4 功能开关和发布解耦

可以先部署包含新功能的代码，但默认关闭；待服务端、配置、数据和监控准备好后再逐步开启。

但功能开关不能代替：

- 代码审查；
- 测试；
- 权限检查；
- 数据兼容；
- 清理过期开关；
- 紧急回滚。

## 25. CI/CD：把手工流程变成可重复流水线

### 25.1 CI 和 CD 分别是什么

```text
CI（Continuous Integration）：持续集成
CD（Continuous Delivery/Deployment）：持续交付/持续部署
```

典型流水线：

```text
push / Pull Request / tag
  → 拉取固定 commit
  → 安装锁定依赖
  → typecheck/lint/test
  → 双构建
  → 生成发布 manifest
  → 生成产物和 SHA-256
  → 安全/SBOM 扫描
  → 上传产物库
  → 部署到测试环境
  → 自动验收
  → 人工审批
  → 生产发布
  → 健康检查/冒烟测试
  → 监控和自动/人工回滚
```

GitHub Actions 的 workflow 由事件触发，包含 jobs 和 steps，在 runner 上执行。参见 [GitHub Actions 官方概念](https://docs.github.com/en/actions/get-started/understand-github-actions)。GitLab CI、Jenkins、Azure DevOps、Gitea Actions 等也可实现类似流程。

### 25.2 Continuous Delivery 和 Continuous Deployment 的区别

- Continuous Delivery：任何通过门禁的版本都随时可发布，生产切换可保留人工批准；
- Continuous Deployment：通过所有门禁后自动发布到生产。

对当前项目，建议先做 Continuous Delivery：

```text
自动测试、构建、打包、校验、上传产物
+ 人工审批生产切换
```

不要在测试覆盖不足时直接跳到“每次 push main 自动上生产”。

### 25.3 “只构建一次，逐环境提升同一产物”

不成熟做法：

```text
测试环境构建一次
生产环境又从同一 commit 重新构建一次
```

即使 commit 一样，依赖镜像、工具版本、时间和环境差异也可能产生不同产物。

推荐：

```text
构建一次不可变产物
→ 产物进入受保护仓库
→ 同一 SHA-256/digest 逐步提升到 test/staging/production
```

环境差异应尽量由运行配置提供，而不是重新生成一份无法证明与测试产物一致的二进制。

## 26. 建议本项目采用的版本映射表

为每次发布生成一份机器可读 manifest，例如：

```json
{
  "application": "scene-library",
  "productVersion": "0.2.0",
  "releaseId": "20260818-144540",
  "git": {
    "commit": "<完整 commit SHA>",
    "branch": "main",
    "tag": "v0.2.0",
    "dirty": false
  },
  "build": {
    "createdAt": "2026-08-18T14:45:40+08:00",
    "node": "22.23.2",
    "command": "npm run build:all"
  },
  "protocols": {
    "hostNavigation": "1.0"
  },
  "artifacts": [
    {
      "name": "scene-library-release-20260818-144540.tar.gz",
      "sha256": "<SHA-256>"
    }
  ]
}
```

专业要点：

- `dirty: false`：产物应由已提交源码构建；
- 使用完整 commit SHA，不只保存 7 位缩写；
- 产物 hash 和文件名一起记录；
- 协议版本与产品版本分开；
- 构建工具版本可追踪；
- manifest 跟产物一起保存，也可上传到发布系统。

健康接口可返回精简版：

```json
{
  "status": "ok",
  "version": "0.2.0",
  "releaseId": "20260818-144540",
  "commit": "b4ec6eb..."
}
```

不应在公开健康接口暴露密钥、服务器绝对路径、内网凭据等敏感信息。

## 27. 从当前项目走向业内成熟水平的路线图

### 阶段 1：可追踪手工发布

- 每次发布前保证 Git 工作区干净；
- 使用功能分支和代码审查；
- 建立 SemVer + release ID + commit 映射；
- 自动生成 release manifest；
- 保留发布和回滚记录；
- 定期演练回滚。

### 阶段 2：自动构建和测试

- Pull Request 自动 lint/typecheck/test/build；
- 将历史 TypeScript 阻断项修复到可作为门禁；
- 添加核心页面 E2E 测试；
- 添加主平台/场景库协议契约测试；
- CI 生成不可变发布包和 SHA-256；
- 产物进入正式产物库。

### 阶段 3：可审批的自动交付

- 自动部署测试环境；
- 自动冒烟测试；
- 生产发布需人工审批；
- 部署使用低权限账号和受保护凭据；
- 流水线自动建立 `previous`、切换、健康检查；
- 失败自动回滚并通知。

### 阶段 4：高可靠与供应链安全

- HTTPS 和证书自动化；
- 产物签名和 provenance；
- SBOM 和依赖漏洞管理；
- 结构化日志、指标、告警和发布标记；
- 蓝绿/金丝雀发布；
- 容量管理和压力测试；
- 备份恢复和容灾演练；
- 安全事件响应和密钥轮换。

### 阶段 5：平台化

当服务和团队规模足够大时，再评估：

- 容器化；
- Kubernetes/托管容器平台；
- GitOps；
- 内部开发者平台；
- 服务目录；
- 统一流水线模板；
- 策略即代码；
- 多地域、多集群和容灾。

技术大拿的特征不是会背最多命令，而是：

```text
能把复杂系统拆成边界清晰的问题；
能用证据而不是感觉做判断；
能为失败设计回滚和恢复；
能根据业务规模选择恰当的复杂度；
能将知识固化为自动化、文档和可复用平台。
```

## 28. 建议的实战练习

### 练习 1：在安全分支理解 Git 四个区域

1. 新建练习分支；
2. 修改一份文档；
3. 查看 `git diff`；
4. `git add` 后对比 `git diff --cached`；
5. 提交；
6. 使用 `git show` 查看 commit；
7. 使用 `git revert` 生成反向提交。

### 练习 2：生成 release manifest

写一个脚本自动收集：

```text
Git commit
Git dirty 状态
Node/npm 版本
构建时间
产物文件名
SHA-256
```

如果工作区 dirty，脚本拒绝生成正式发布包。

### 练习 3：在临时目录模拟 release 切换

不操作生产，在临时 Linux 目录建立：

```text
releases/v1
releases/v2
current
previous
```

练习：

- 将 current 指向 v1；
- 发布 v2 前把 previous 指向 v1；
- 将 current 切到 v2；
- 模拟验证失败；
- 回滚到 previous；
- 验证整个过程不覆盖 release 内容。

### 练习 4：比较完整包和块更新

1. 准备一个大文件；
2. 仅改变中间少量字节；
3. 比较整文件重下和固定分块更新量；
4. 再在文件开头插入字节，观察固定分块的偏移效应；
5. 了解滚动分块/内容定义分块为什么能改善跨位移复用。

### 练习 5：设计一个客户端/服务端兼容矩阵

```text
Server 1.0 / 1.1 / 2.0
Client 1.0 / 1.1 / 2.0
```

对每个组合标注：

- 完全支持；
- 只读；
- 功能降级；
- 必须更新；
- 不允许连接。

这个练习会让你从“只想最新版”进阶到“设计可演进系统”。

## 31. 最后的工程心法

发布不是把“代码从 A 复制到 B”这么简单。

真正成熟的发布系统要同时回答：

```text
可追踪：它从哪个 commit 来？
可重复：同样输入能否得到可验证产物？
可验证：我怎么知道包没损坏、功能正常？
可信：  我怎么知道它由正确发布者生成？
可审计：谁在什么时候把什么发到了哪里？
可观测：新版本上线后是否真的正常？
可回滚：失败后多久能恢复？
可兼容：新旧前端、后端、数据和协议能否共存？
可演进：系统规模扩大时，现有方法怎样平滑升级？
```

从 Git 开始，你学到的不应只是几条命令，而是“把每一次变更变成可理解、可审查、可恢复的工程记录”。再将这种思维延伸到构建、产物、环境、监控和自动化，就是从“会写代码”走向“能负责生产系统”的关键路径。
