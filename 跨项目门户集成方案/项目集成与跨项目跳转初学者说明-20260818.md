## 阅读前先明确四个边界

为了避免把“运行现象”和“安全保证”混在一起，先记住下面四点。后文建议始终按“概念是什么 → 本项目怎样使用 → 能做什么 → 不能保证什么 → 出错怎样排查”的顺序阅读。

1. `window.parent === window` 只用于判断当前页面有没有被其他窗口嵌入。它不是身份认证，也不能证明父页面一定是可信的主平台。真正的消息安全仍依赖接收端同时校验 `event.source`、`event.origin`、协议字段和业务白名单。
2. 场景库独立访问时，可以把当前浏览器页直接导航到主平台模型详情地址；但主平台仍可能经过登录、权限和路由守卫。这属于正常的主平台访问控制，场景库不能绕过。
3. 主平台执行 `router.push` 后，场景库所在 iframe 可能因为宿主路由的 `ignoreKeepAlive: true` 而立即销毁。因此，成功响应不一定来得及被场景库显示；页面是否正确到达目标路由才是成功的最终依据。拒绝或失败响应则应尽量明确返回。
4. 当前资料同时出现 `http://8.146.211.204:3100` 和 `http://8.146.211.204`。它们确切对应开发、联调还是生产环境，应由主平台团队按实际 Nginx 和部署配置确认，不能仅凭端口号下结论。

## 1. 先用一句话理解整个方案

主平台像一座商场，场景库像被嵌入商场的一家独立店铺。

主平台使用 iframe 把场景库的完整网页放进自己的“场景库”页面中。当场景库想打开主平台的“模型详情”时，它不直接操作主平台，而是通过 `postMessage` 告诉主平台：

```text
“请帮我打开模型 2326 的详情页。”
```

主平台收到请求后，校验请求是否安全，再用自己的 Vue Router 执行页面跳转。主平台原有的内标签系统会自动决定：

- 内标签开启：打开一个主平台内部页签；
- 内标签关闭：当前浏览器页直接进入模型详情页。

这就是本项目的集成和跨项目跳转方式。

## 3. 什么是 iframe

### 3.1 最简单的理解

iframe 可以理解为“网页里的另一个网页窗口”。

一个简化例子：

```html
<iframe src="http://47.122.104.52:8081/cockpit/"></iframe>
```

这段代码的含义是：

```text
当前页面中预留一块区域，
再把 http://47.122.104.52:8081/cockpit/ 这个完整网页放进去。
```

主平台当前的场景库页面就是这样实现的。

### 3.2 iframe 里面和外面分别是什么

```text
浏览器标签页
└─ 主平台（父页面）
   ├─ 主平台左侧菜单
   ├─ 主平台顶部内标签
   └─ 场景库 iframe（子页面）
      ├─ 场景库左侧菜单
      ├─ 场景库仿真页面
      └─ “查看资源详情”按钮
```

这里有两套前端程序：

- iframe 外面是 Vue 主平台；
- iframe 里面是 React 场景库。

虽然视觉上看起来在同一个页面中，但它们仍然是两个独立程序。

### 3.3 本项目为什么不是 qiankun

qiankun 是一种微前端框架，可以把多个前端应用按生命周期挂载到主应用中。

本项目早期曾讨论过 qiankun，但主平台实际选择的集成方式是 iframe。因此当前事实是：

- 不使用 qiankun 的 `bootstrap/mount/unmount` 完成集成；
- 不通过 qiankun props 传递导航函数；
- 不把 React 组件直接注入 Vue 页面；
- 主平台只需要使用 iframe 加载场景库独立页；
- 跨项目导航使用浏览器标准 `postMessage` 通信。

## 4. 先分清三种“标签或页面”

这是理解需求时最容易混淆的地方。

### 4.1 浏览器标签页

这是 Chrome、Edge 最顶部的标签。

```text
[主平台] [搜索引擎] [文档]
```

旧的实现使用：

```html
<a href="..." target="_blank">查看资源详情</a>
```

`target="_blank"` 表示打开一个新的浏览器标签页。这正是本次需要弃用的方式。

### 4.2 主平台内标签

内标签是主平台自己页面里的标签栏，不是浏览器标签。

例如：

```text
浏览器标签：[主平台]

主平台页面内部：
[首页] [场景库] [模型详情 ×]
```

用户仍然只打开了一个浏览器标签，但主平台内部可以管理多个业务页签。

### 4.3 同页路由跳转

当主平台内标签关闭时，仍然不新建浏览器标签。

主平台用 Vue Router 把当前显示的业务内容从场景库切换为模型详情：

```text
跳转前：http://8.146.211.204:3100/scene-library
跳转后：http://8.146.211.204:3100/three-model/detail?id=2326
```

这是单页应用内部的路由切换，不是“在场景库页面里再嵌套一个模型页面”。

## 5. 什么是前端路由

### 5.1 路由是地址和页面的对应关系

例如：

| 地址 | 显示的页面 |
|---|---|
| `/scene-library` | 场景库宿主页 |
| `/three-model/query` | 模型查询/列表页 |
| `/three-model/detail?id=2326` | ID 为 2326 的模型详情页 |

### 5.2 `path` 和 `query`

这个地址：

```text
/three-model/detail?id=2326
```

可以拆成：

```text
path  = /three-model/detail
query = id=2326
```

在 Vue Router 中，推荐写法是：

```ts
router.push({
  path: '/three-model/detail',
  query: { id: '2326' },
});
```

它的意思是：

```text
请主平台切换到模型详情页，
并告诉详情页需要加载模型 2326。
```

### 5.3 为什么不在 iframe 中直接调用 `router.push`

因为 `router` 属于主平台 Vue 应用。场景库 iframe 中运行的是另一个 React 应用，它没有主平台的 `router` 对象。

即使试图访问：

```ts
window.parent.router
```

也会因为两个项目的 Origin 不同而被浏览器的安全策略阻止，且主平台本身也没有把 router 挂到 `window` 上。

## 6. 什么是 Origin，为什么这里是跨域

### 6.1 Origin 由三部分组成

```text
协议 + 主机 + 端口
```

例如：

```text
http://47.122.104.52:8081
│      │             └─ 端口
│      └─ IP/主机
└─ 协议
```

两个地址要想“同源”，这三部分都必须相同。

### 6.2 本项目的两个 Origin

```text
主平台：http://8.146.211.204:3100
场景库：http://47.122.104.52:8081
```

IP 和端口都不同，所以它们是跨域的。

跨域 iframe 的安全隔离意味着：

- 场景库不能读取主平台 DOM；
- 场景库不能读取主平台 Pinia Store；
- 场景库不能知道内标签开关的实时值；
- 场景库不能直接调用主平台 Vue Router；
- 主平台也不能随意读取 iframe 内部 DOM。

但浏览器允许两者使用 `postMessage` 安全地传递结构化消息。

## 7. 什么是 `postMessage`

### 7.1 把它理解成“窗口之间传纸条”

场景库不能走进主平台的办公室直接操作电脑，但可以递进一张写清楚需求的纸条。

场景库端发送：

```ts
window.parent.postMessage(
  {
    type: 'scene-library:navigate',
    protocolVersion: '1.0',
    requestId: '...',
    source: 'scene-library',
    target: {
      path: '/three-model/detail',
      query: { id: '2326' },
    },
    openMode: 'host-default',
    modelName: '水轮机总成',
  },
  '主平台的 Origin',
);
```

主平台端监听：

```ts
window.addEventListener('message', handleSceneLibraryMessage);
```

可以将两句代码理解为：

```text
场景库：我把导航请求发给父页面。
主平台：我监听收件箱，收到后检查并处理。
```

### 7.2 只发送“导航意图”

场景库发送的不是“帮我直接修改主平台标签数组”，而是：

```text
我想打开 /three-model/detail，模型 ID 是 2326。
```

主平台保留最终决定权：

- 请求是否来自正确的 iframe；
- 是否来自允许的 Origin；
- 路由是否在白名单；
- 模型 ID 是否允许；
- 当前用户是否有权限；
- 应否被路由守卫拦截。

这种“子页只提出请求，父页负责执行”的方式，既清晰又安全。

### 7.3 为什么还要返回结果

主平台处理后，应回复：

```ts
{
  type: 'scene-library:navigate-result',
  protocolVersion: '1.0',
  requestId: '与请求一致',
  status: 'accepted',
  mode: 'multi-tab',
}
```

这样场景库可以知道：

- 主平台确实收到了请求；
- 请求被接受、拒绝还是执行失败；
- 主平台当前是内标签模式还是同页模式；
- 失败时应向用户显示什么原因。

`requestId` 就像快递单号，用于确认回复对应哪一次点击。

这里有一个重要的工程边界：如果 `router.push` 成功后立刻销毁了场景库 iframe，场景库可能来不及收到或展示 `accepted`。所以响应协议很有价值，但不能把“收到 accepted”当成唯一成功标准：

- 页面已经正确进入模型详情页：导航成功；
- 页面仍停留在场景库：再根据 `rejected`、`failed` 或超时信息排查；
- 主平台在执行跳转前发现校验失败：应先回传拒绝结果，并且不要跳转。

## 8. 用户点击后到底发生了什么

以“水轮机总成，ID=2326”为例。

### 第 1 步：用户点击按钮

用户在场景库仿真页中点击：

```text
查看资源详情
```

它已经不再是一个带 `_blank` 的普通链接，而是调用统一的点击处理函数。

### 第 2 步：场景库检查模型

场景库检查：

```text
ID          = 2326
模型名称    = 水轮机总成
目标 path = /three-model/detail
目标 query= id=2326
```

如果 ID、名称和地址不匹配，场景库自己就会阻止请求。

### 第 3 步：场景库判断自己是否在 iframe 中

简化判断：

```ts
window.parent === window
```

- 结果为 `true`：场景库是独立访问；
- 结果为 `false`：场景库在 iframe 中。

### 第 4A 步：独立访问时

如果场景库不在 iframe 中，它会在当前浏览器标签中直接访问：

```text
http://8.146.211.204:3100/three-model/detail?id=2326
```

使用的是当前页导航，不是 `_blank`，所以不会新建浏览器标签。

到达主平台后，主平台自己的登录、权限和路由守卫仍然有效。例如登录已过期时，用户可能先被带到登录页；这不是场景库导航失败，而是主平台在执行正常的访问控制。

### 第 4B 步：iframe 集成时

如果场景库在 iframe 中，它不直接跳转，而是发送：

```json
{
  "type": "scene-library:navigate",
  "protocolVersion": "1.0",
  "requestId": "本次点击的唯一编号",
  "source": "scene-library",
  "target": {
    "path": "/three-model/detail",
    "query": { "id": "2326" }
  },
  "openMode": "host-default",
  "modelName": "水轮机总成"
}
```

`host-default` 的意思是：

```text
场景库不指定必须用哪种标签模式，
请主平台根据自己当前设置决定。
```

### 第 5 步：主平台检查消息

主平台必须检查：

1. 消息是否来自当前场景库 iframe；
2. Origin 是否精确为 `http://47.122.104.52:8081`；
3. 消息类型是否为 `scene-library:navigate`；
4. 协议版本是否为 `1.0`；
5. 路由是否只是 `/three-model/detail`；
6. ID 是否属于允许的四个 ID。

不合法就拒绝，合法才进入下一步。

### 第 6 步：主平台执行 `router.push`

```ts
router.push({
  path: '/three-model/detail',
  query: { id: '2326' },
});
```

这一步只负责路由导航，不直接新建内标签。

### 第 7 步：主平台内标签系统自动响应

主平台现有机制大致是：

```text
router.push
   ↓
路由发生变化
   ↓
路由变更事件被发送
   ↓
MultipleTabs 监听到新路由
   ↓
新增、复用或激活主平台内标签
```

如果内标签开关关闭，`MultipleTabs` 组件不挂载，所以同一次 `router.push` 只表现为普通同页跳转。

### 第 8 步：主平台回复处理结果

成功时回复：

```json
{
  "type": "scene-library:navigate-result",
  "protocolVersion": "1.0",
  "requestId": "与请求相同",
  "status": "accepted",
  "mode": "multi-tab"
}
```

如果在 5 秒内没有收到回复且页面也没有导航，场景库显示：

```text
主平台未响应模型详情跳转请求，请稍后重试。
```

注意这里有两个条件：“没有收到回复”并且“页面也没有导航”。如果模型详情已经正常打开，即使旧 iframe 没来得及收到 `accepted`，也不应再把它解释成失败。

## 9. 为什么只改场景库还不够

这是本次最重要的架构概念。

### 9.1 发消息和处理消息是两件事

场景库可以单方执行：

```ts
window.parent.postMessage(...);
```

但发出消息不代表主平台会自动理解它。

主平台必须有：

```ts
window.addEventListener('message', ...);
```

这就像：

```text
场景库把信放到了主平台门口，
但主平台如果没有收信人，信不会自己变成页面跳转。
```

当前出现“主平台未响应”，就是因为场景库端已经发信，但主平台的收信代码还没有开发和发布。

### 9.2 场景库不知道内标签开关

开关保存在主平台 Pinia 状态中：

```text
multiTabsSetting.show
```

场景库 iframe 因为跨域，不能读取它。

即使读到了一个开关值，场景库也不应跨越边界去操作主平台标签数组。这些都应归主平台管理。

### 9.3 什么情况下可以只改场景库

只有主平台已经存在一个通用 iframe 导航接口，并且已经提供完整的消息协议时，才可以只让场景库去适配该接口。

主平台已提供的资料明确说明：

- 当前宿主页没有 `postMessage` 通信；
- 没有统一 iframe 通信封装；
- 需要在 `src/views/sceneLibrary/index.vue` 增加最小消息监听和 `router.push`。

因此本次需要两个项目各完成自己的一半。

## 10. 旧方法与新方法对比

| 对比项 | 旧方法 | 新方法 |
|---|---|---|
| 场景库入口 | `<a target="_blank">` | 点击处理函数 |
| 浏览器行为 | 新建浏览器标签 | 不新建浏览器标签 |
| iframe 内导航 | 直接打开 URL | 通过 `postMessage` 请求主平台导航 |
| 内标签适配 | 不支持 | 主平台 `router.push` 自动适配 |
| 开关关闭 | 仍新建浏览器标签 | 同一浏览器页内路由切换 |
| 安全范围 | 链接可直接打开 | 主平台校验 Origin、path 和 ID |
| 失败处理 | 依赖浏览器新窗口 | 页内提示、不回退到 `_blank` |
| 影响范围 | 原有四页链接 | 仍仅四页的模型详情入口 |

## 12. 主平台内标签是怎样自动适配的

### 12.1 开关在哪里

主平台的内标签开关可简化理解为：

```ts
multiTabsSetting.show
```

### 12.2 开关打开时

```text
multiTabsSetting.show = true
        ↓
MultipleTabs 组件显示并监听路由
        ↓
router.push 后自动增加/复用内标签
```

### 12.3 开关关闭时

```text
multiTabsSetting.show = false
        ↓
MultipleTabs 组件不挂载
        ↓
router.push 只做普通同页路由切换
```

### 12.4 为什么不需要写两套跳转逻辑

主平台无论开关开还是关，都只执行：

```ts
router.push({ path, query });
```

区别只是 `MultipleTabs` 组件当前是否存在。

所以正确思路不是：

```text
场景库查开关 → 分别执行两种导航
```

而是：

```text
场景库发送导航意图
        ↓
主平台统一 router.push
        ↓
主平台现有内标签机制自动适配
```

## 13. 为什么要做白名单校验

### 13.1 不能盲目信任消息

页面上的消息可能来自：

- 正常场景库 iframe；
- 浏览器扩展；
- 其他 iframe；
- 错误配置的页面；
- 恶意页面或人工构造的消息。

如果主平台收到任意 path 都直接跳转，可能形成未授权导航、异常页面或安全问题。

### 13.2 需要检查什么

```text
消息窗口：必须是当前场景库 iframe
Origin：     必须是 http://47.122.104.52:8081
消息类型：   必须是 scene-library:navigate
协议版本：   必须是 1.0
路由：       必须是 /three-model/detail
模型 ID：    必须是 2326/2328/2316/2310 之一
```

### 13.3 为什么 `targetOrigin` 不能写 `*`

`*` 表示“不管对方是谁都可以收”。

在本项目中应指定精确 Origin，避免消息被错误窗口收到。

## 14. 初学者容易误解的地方

### 误解 1：在同一个浏览器页里，就是同一个项目

不对。iframe 只是把一个独立项目显示在另一个项目里。它们仍有独立源码、独立运行环境和安全边界。

### 误解 2：场景库发出 `postMessage` 就能自动跳转

不对。`postMessage` 只负责送信。主平台必须编写收信、校验和处理代码。

### 误解 3：主平台要为内标签开/关写两个函数

不需要。主平台两种状态都用 `router.push`，现有 `MultipleTabs` 组件自动适配。

### 误解 4：主平台只要修改源码，不发布也能生效

不对。用户访问的是服务器实际运行或 Nginx 实际提供的产物。只改仓库文件，没有构建、切换产物或重启对应服务，浏览器仍会使用旧代码。

### 误解 5：跳转失败时再用 `_blank` 保底更好

不对。这会重新引入需求明确禁止的新浏览器标签。失败时应页内提示和记录原因。

### 误解 6：场景库中的 API ONLINE 说明跳转也必然正常

不对。API ONLINE 只表示场景库可以获取业务数据。跨项目导航是另一条通信链路，需要主平台消息监听和 Vue Router 配合。

## 16. 如何判断集成是否成功

### 16.1 正常的最终现象

内标签开启时：

```text
点击查看资源详情
  → 浏览器没有新增标签
  → 主平台内部出现/激活“模型详情”标签
  → 模型 ID 和页面内容正确
```

内标签关闭时：

```text
点击查看资源详情
  → 浏览器没有新增标签
  → 当前主平台页直接变为模型详情
  → 不是 iframe 里再嵌套一个详情页
```

### 16.2 当前“主平台未响应”代表什么

它代表：

```text
场景库新版本已经运行，并已发出请求；
但主平台的消息处理代码尚未发布或未正常工作。
```

它不代表：

- 场景库 API 必然断开；
- 模型数据必然错误；
- 按钮没有发出任何事件；
- 应该恢复 `_blank`。

## 17. 初学者排查清单

遇到问题时，按下列顺序检查，不要一开始就同时修改两个项目。

### 第 1 层：场景库是否正常加载

```text
http://47.122.104.52:8081/cockpit/
```

能否正常显示？

### 第 2 层：场景库 API 是否正常

```text
http://47.122.104.52:8081/scene-library-api/health
```

当前应返回：

```json
{"status":"ok","version":"20260818-144540"}
```

### 第 3 层：是否只有跳转失败

如果页面、数据和三维资源都正常，仅点击详情时出现“主平台未响应”，则优先检查主平台消息监听，而不是场景库 API。

### 第 4 层：主平台是否收到消息

联调时可在主平台处理器中临时记录：

```ts
console.debug('[scene-library] message received', {
  origin: event.origin,
  type: event.data?.type,
  requestId: event.data?.requestId,
});
```

没日志时检查监听是否注册；有日志时继续检查 Origin、path 和 ID。

### 第 5 层：主平台是否执行路由导航

检查地址栏是否变成：

```text
/three-model/detail?id=<当前模型ID>
```

如果地址正确但没有内标签，再检查主平台的标签开关、路由 meta 和 `MultipleTabs` 监听。

### 第 6 层：浏览器是否在用旧产物

如果源码已经修改，但线上仍然没有变化，检查：

- 是否执行了构建；
- 是否发布到真正对外的目录；
- `3100` 和 `80` 是否是两个不同环境；
- 进程是否已按正确方式重启；
- 浏览器是否缓存了旧 JavaScript；
- 无痕窗口或强制刷新后是否恢复。

## 18. 本方案的优点与局限

### 18.1 优点

- 两个项目可以独立开发和部署；
- 主平台不需要复制场景库源码；
- 不需要改造主平台全局内标签系统；
- 使用浏览器标准 API，不绑定微前端框架；
- 可以对 Origin、路由和 ID 做明确白名单；
- 两种内标签状态复用同一条 `router.push`；
- 场景库独立访问仍然可用。

### 18.2 局限

- iframe 与主平台存在天然隔离，通信必须通过协议；
- 两端的 Origin 变更后需同步调整安全白名单；
- 主平台从场景库跳到模型详情时，场景库宿主路由当前配置了 `ignoreKeepAlive: true`；
- 返回场景库内标签时，iframe 会重新加载，可能回到场景库默认页；
- 如未来主平台使用 HTTPS，仍嵌入 HTTP 场景库会遇到混合内容问题，需配置 HTTPS 或同源代理。

## 20. 最后的记忆要点

如果只记住七件事，记住下面这些：

1. 主平台是 Vue，场景库是 React，它们是两个独立项目。
2. 主平台用 iframe 把场景库独立页嵌入到自己页面中。
3. 当前集成方式不是 qiankun。
4. 两个系统跨域，场景库不能直接调用主平台 Vue Router。
5. 场景库用 `postMessage` 发送导航意图，主平台校验后执行 `router.push`。
6. 内标签开和关都用同一个 `router.push`，主平台现有标签机制自动适配。
7. 两端代码都发布后，跨项目跳转才算完整上线。
