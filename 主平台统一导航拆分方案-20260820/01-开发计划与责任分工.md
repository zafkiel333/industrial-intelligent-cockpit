# 场景库导航拆分：开发计划与责任分工

## 1. 开发目标

在不改变 iframe 集成和现有云部署结构的前提下，实现：

- 主平台只出现一个一级菜单“场景库”；
- 场景库现有菜单树整体迁移到“场景库”下一级；
- iframe 内不显示场景库全局左侧导航和顶部平台栏；
- 主平台点击菜单后，场景库展示正确 `viewId` 对应页面；
- 直接访问场景库时仍可保留原导航，方便独立测试和故障排查；
- 已有模型详情跨项目跳转继续正常；
- 双方都能独立发布和回滚。

---

## 2. 设计原则

1. **主平台拥有导航，场景库拥有内容。**
2. **菜单树只整体下移一级，不改变业务层级。**
3. **页面定位只传稳定 `viewId`，不传 React 组件名或文件路径。**
4. **第一版使用 URL 参数，优先可理解、可刷新和可排错。**
5. **保留旧入口兼容，确保可以分两次发布。**
6. **菜单清单机器生成，避免人工复制大量项目。**
7. **双方分别校验输入，不能因为来源是合作系统就完全信任。**
8. **不扩大到主平台全局标签系统和其他业务菜单。**

---

## 3. 阶段划分

### 阶段 A：协议和菜单快照冻结

场景库侧：

- 确认当前 `MENU_ITEMS` 为迁移基线；
- 检查所有 `viewId` 唯一；
- 检查父子结构无循环；
- 生成完整 `scene-library-menu.manifest.json`；
- 为菜单清单生成版本号和 SHA-256；
- 将协议文档与清单交给主平台。

主平台侧：

- 确认菜单落库/注册方式；
- 确认权限粒度；
- 确认内标签策略；
- 确认开发和生产路由来源。

完成门槛：双方对 `viewId`、URL、菜单层级和默认页没有歧义。

### 阶段 B：场景库兼容开发

主要改动：

- 独立入口读取 URL 参数；
- `embedded=1` 时隐藏 Sidebar；
- `viewId` 校验与默认回退；
- 为无效参数增加日志和可选提示；
- 保持无参数访问方式不变；
- 增加相关测试。

完成门槛：新旧地址都能正确打开。

### 阶段 C：场景库先行部署

原因：新版场景库兼容旧主平台；旧版场景库不认识新参数。

部署后状态：

- 主平台尚未修改时仍看到旧导航，不中断使用；
- 新参数地址可提前由浏览器直接验收；
- 场景库有独立回滚版本。

### 阶段 D：主平台开发

主要改动：

- 将原菜单树挂到“场景库”一级菜单下；
- 菜单项记录 `viewId`；
- `/scene-library` 接收 `viewId` query；
- iframe `src` 附加 `embedded=1&viewId=...`；
- 菜单点击、刷新、权限和标签标题适配；
- 保留已有模型详情消息监听。

完成门槛：主平台本地/测试环境可以通过不同菜单打开正确场景页面。

### 阶段 E：联合测试

至少覆盖：

- 一级、二级、三级及最深层菜单；
- 默认页和非法 `viewId`；
- 刷新、返回、前进；
- 内标签开/关；
- 权限允许/拒绝；
- 3D、图表、数据接口和上传类页面；
- 场景库到模型详情的已有跳转；
- 主平台和场景库任一端回滚后的兼容性。

### 阶段 F：主平台发布

主平台按自己的代码、后台菜单和 Nginx 流程发布。场景库团队不登录主平台服务器。

发布完成后进行生产联合验收，并记录双方版本。

## 5. 预计涉及文件

### 场景库

| 文件/模块 | 预计调整 |
|---|---|
| `index.tsx` | 读取并校验 `embedded`、`viewId`，传给 `App` |
| `App.tsx` | 嵌入模式不渲染 `Sidebar`；继续按 `viewId` 切换内容 |
| `src/integration/menu.ts` | 复用/扩展菜单查找、默认页和校验函数 |
| `constants.tsx` | 继续作为当前菜单树数据源，不在此需求中重写页面 |
| 新的 manifest 生成脚本 | 输出纯 JSON 菜单清单和版本信息 |
| 测试文件 | 覆盖参数解析、非法 ID、独立/嵌入布局 |

### 主平台

| 文件/模块 | 预计调整 |
|---|---|
| 菜单后台或菜单配置 | 建立“场景库”一级和其完整子树 |
| `src/router/routes/modules/sceneLibrary.ts` | 允许 query 定位；根据最终菜单来源调整隐藏配置 |
| `src/views/sceneLibrary/index.vue` | 读取 `viewId`，安全生成 iframe src |
| 菜单权限配置 | 按确认粒度配置 |
| 内标签标题逻辑（如需） | 根据菜单标题显示，不改变全局标签框架 |
| 现有消息监听 | 保留场景库到模型详情导航处理 |

文件位置以主平台当前分支实际代码为准。

## 6. 风险与控制

| 风险 | 控制方法 |
|---|---|
| 菜单数量大，人工录入出错 | 使用 manifest 和导入脚本 |
| 两端菜单版本不一致 | manifest 带版本、生成时间和 SHA-256 |
| 非法 ID 导致空白页 | 双端白名单校验并回退默认页 |
| query 拼接导致编码问题 | 使用 `URL`/`URLSearchParams`，不手拼字符串 |
| 页面切换导致 iframe 重载 | 第一版接受；实测不满足再升级消息切页 |
| 多个 query 产生大量内标签 | 主平台开发前确认标签复用策略 |
| 主平台菜单权限过细导致工作量大 | 先确定权限粒度，再导入 |
| 新旧版本发布顺序错误 | 场景库先发布，主平台后发布 |
| 回滚后两端不兼容 | 场景库无参数旧入口必须保留 |
| 现有模型详情跳转被破坏 | 独立列为回归用例 |

---

## 7. 完成定义

只有满足以下全部条件，本需求才算完成：

- 主平台只出现一个本项目一级菜单“场景库”；
- 原 20 个根菜单成为“场景库”的二级菜单；
- 原 children 层级和排序得到保留；
- iframe 中不再出现场景库 Sidebar 和自身顶部平台栏；
- 所有有效 `viewId` 可以打开正确页面；
- 无效 ID 不产生白屏；
- 页面刷新可恢复；
- 内标签策略符合主平台确认结果；
- 模型详情跳转未回归；
- 两端分别完成部署和版本记录；
- 回滚演练或至少回滚路径检查通过。
