# 场景库导航拆分至主平台：方案总览与文档交付清单

> 文档日期：2026-08-20  
> 适用系统：主平台 `ices-union` 与场景库 `industrial-intelligent-cockpit`  
> 当前集成方式：主平台使用 iframe 加载场景库独立版，不使用 qiankun  
> 本文件是本次需求的总入口。

---

## 1. 一句话结论

主平台只保留一个关于本项目的一级菜单“场景库”；场景库现有整棵菜单树原样下移一级，由主平台负责显示和点击导航，iframe 中的场景库不再显示自己的全局左侧导航，只负责渲染指定 `viewId` 对应的业务内容。

```text
主平台
└─ 场景库                         一级菜单，主平台唯一的本项目入口
   ├─ 工业智能运维                原场景库一级菜单，迁移后为二级
   │  ├─ 水轮机智能运维           原二级，迁移后为三级
   │  └─ ……
   ├─ 工业产品知识库              二级
   ├─ 运行驾驶舱                  二级
   ├─ 仿真分析                    二级
   └─ ……
```

“整体下移一级”意味着保留原菜单父子关系和排序，不把所有叶子页面压平成场景库的直接子项。

---

## 2. 本次采用的最简实现

第一版使用 URL 参数传递页面定位，不新增主平台到场景库的 `postMessage` 协议：

```text
主平台地址：
/scene-library?viewId=sim-visual-hydro-turbine

iframe 地址：
http://47.122.104.52:8081/cockpit/?embedded=1&viewId=sim-visual-hydro-turbine
```

参数含义：

- `embedded=1`：场景库进入嵌入模式，不显示自己的左侧导航和顶部平台栏；
- `viewId=...`：场景库只显示该页面；
- 未传或传入无效 `viewId`：回到双方约定的默认页，并产生可排查的提示/日志。

选择 URL 参数的原因：

- 和当前 iframe 架构直接兼容；
- 刷新后仍能恢复当前页面；
- 无需增加握手、消息时序和重试逻辑；
- 地址本身即可用于排错；
- 不改变已有“场景库 → 主平台模型详情”的 `postMessage` 协议。

如果将来实测发现 iframe 重载成本不可接受，再升级为“URL 首次定位 + `postMessage` 后续切页”。这不属于第一版必须范围。

## 4. 双方改动边界

### 场景库侧负责

- 从地址读取 `embedded` 和 `viewId`；
- 嵌入时不渲染 `Sidebar` 和自身顶部平台栏；
- 根据 `viewId` 渲染既有页面；
- 校验 `viewId`；
- 从当前 `MENU_ITEMS` 生成不含 React 代码的菜单清单；
- 保持独立访问兼容；
- 保留现有模型详情跳转协议；
- 构建、发布并提供可回滚版本。

### 主平台侧负责

- 只建立一个一级菜单“场景库”；
- 将场景库菜单树挂到“场景库”之下；
- 处理菜单权限、排序、图标和展开行为；
- 点击场景菜单时设置主平台 `viewId`；
- 在 iframe 地址中安全传入 `embedded=1&viewId=...`；
- 处理主平台内标签标题和是否复用标签；
- 继续处理已有场景库模型详情导航消息；
- 按主平台自己的流程发布。

### 明确不做

- 不迁移场景业务页面源码到主平台；
- 不改用 qiankun；
- 不让场景库操作主平台 DOM、Pinia 或菜单数组；
- 不修改场景库 API 前缀、端口和服务器目录；
- 不删除场景库独立访问能力；
- 不在第一版增加主平台到场景库的实时切页消息协议；
- 不改造主平台全局内标签框架。

## 7. 主平台收到材料后只需确认的事项

为避免多轮来回沟通，请主平台在开发前一次性确认：

1. 是否能在“场景库”一级菜单下保留原树的多级结构；
2. 菜单来源采用后台菜单导入、构建期导入还是前端静态配置；
3. 每个场景页面是否独立形成主平台内标签，还是始终复用一个“场景库”标签；
4. 生产环境 `/scene-library` 路由是否来自 Jeecg 后台动态菜单；
5. 对 `viewId` query 的权限守卫和刷新恢复是否有额外限制；
6. 场景库菜单权限由主平台逐叶控制，还是仅控制“场景库”总入口；
7. 联调地址和生产地址分别是什么；
8. 主平台预计开发、测试和发布时间窗口。

除上述主平台自身决策外，双方技术传参格式已经在本文件夹中固定，不需要重新发明协议。

建议主平台直接按下面模板一次性回复，减少后续零散确认：

